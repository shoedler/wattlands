# Decisions: relay (`server/relay`)

Short ADRs for the multiplayer relay (BRIEF 5.3). Date for all of them: 2026-10-21.

- **The protocol core is socket-free, and two WebSocket layers sit under it.** `src/relay.ts` gets a `RelayConn` per socket and is fed text. `src/ws_package.ts` (the `ws` package) and `src/ws_builtin.ts` (an RFC 6455 server on `node:http` upgrade and `node:crypto`) only frame bytes. `RELAY_WS_IMPL=auto` (the default) tries `import('ws')` and falls back to the built-in server. `ws` and `builtin` force a choice, and `ws` fails if the package is missing. The server checks the handshake (`src/handshake.ts`) before it hands the socket to either layer, so both refuse bad upgrades the same way (405, 400, 426 with `Sec-WebSocket-Version: 13`, 404). The `ws` layer is set to match the built-in one: `maxPayload` 16384, no permessage-deflate, no subprotocol. *Alternatives:* the built-in server only, or the protocol logic written twice. *Reason:* BRIEF prefers `ws` and requires a zero-dependency fallback. One core lets the same protocol and frame suites prove both layers.
- **Every time rule runs on an injected clock, applied by `sweep()`.** The idle timeout, the token bucket, the join window, reconnect-token expiry, the host hold and the room lifetime all read `Clock.now()`, which is monotonic `performance.now()` in production. `startRelay()` calls `relay.sweep()` every second. Tests use a `FakeClock` with `sweepMs: 0` and sweep by hand, so the 60 s, 120 s and 4 h cases run in milliseconds and are deterministic. A message that arrives for an expired seat or room sweeps that room first, so nothing depends on sweep timing.
- **`hello` comes first.** `create`, `join` and `msg` before `hello` get `bad_request` ("send hello first"); `ping` is allowed at any time. `hello` has no reply. A `proto` other than 1 gets `error {code: "version_mismatch", proto: 1}`, and the socket closes with 4002. *Alternative:* assume protocol 1 when `hello` is missing. *Reason:* the version check only works if every client sends its version, and BRIEF's protocol lists `hello` first.
- **A malformed message is answered, not fatal.** Invalid JSON, a non-object, a missing or unknown `t` (including server-only types like `created`), a missing or mistyped field, or a binary message gets `error {code: "bad_request", detail, re}`, and the connection stays open. Only WebSocket-level faults close the socket: 1002 for a protocol error, 1007 for invalid UTF-8 and 1009 for oversize. *Reason:* a client bug shouldn't drop a rider from a session, and `detail` and `re` make the bug easy to find.
- **The 16 KB limit is enforced in the WebSocket layer, as close code 1009.** It applies to the whole message across fragments. The built-in server checks it from the frame header before buffering the payload. *Alternative:* accept larger frames and answer with `bad_request`. *Reason:* that's standard WebSocket behaviour (`ws` `maxPayload`), it bounds memory per socket, and NetSession never sends more than 16 384 bytes (OWNERSHIP C9), so an oversize message is a client bug.
- **The rate limit is a token bucket of 60 a second, burst 120, per connection, over every message.** That includes `ping`, `hello` and `join`. It is checked before JSON parsing, so floods are cheap to drop. Each dropped message is counted, and at most one `rate_limited` error goes out per connection per second. *Alternative:* an error per dropped message. *Reason:* an error per drop would double a flood back at a misbehaving client.
- **The join limit is a sliding window of 10 attempts a minute per IP.** Only attempts that pass validation count, and refused attempts don't, so a client retrying in a loop gets back in after a minute. Without `RELAY_TRUST_PROXY` the socket address is used, because forwarded headers can be forged. (Revised 2026-11-02: the proxy modes now read the last `X-Forwarded-For` entry or `Fly-Client-IP`, see below.)
- **Seats, peer ids and held seats.** The host is peer 1, and peer ids grow and are never reused in a room. A dropped peer's seat is held 120 s and counts toward `max`. `create.max` is capped at 8, and `created.max` reports the cap. On a drop, every other connected peer gets `peer_left` with reason `dropped`. An explicit leave sends reason `left` and frees the seat at once. Seat expiry sends nothing: the peer already got `peer_left`, and NetSession leaves the slot AFK (OWNERSHIP NET6).
- **A seat keeps one reconnect token until it is freed, and a reconnect may replace a live socket.** (Revised in the hardening review; the first version rotated the token on every reconnect.) A valid token returns the same peer id and the same token (`joined.rejoin: true`), and every other peer gets `peer_joined {rejoin: true}`. The 120 s hold restarts at every drop, and expiry is checked when a `join` arrives, not only by the sweep. If the old socket still looks open (a killed client whose TCP connection the relay hasn't noticed), the new socket takes over: the old one closes with 4001, and the others get `peer_left` (`dropped`) and then `peer_joined` (`rejoin`), the same transitions as a drop. An unknown or expired token joins as a new peer instead of failing, and the host then decides (`session_in_progress`). *Alternatives:* rotate the token on every reconnect, or refuse a token while its socket is open. *Reason:* with rotation, a reconnect whose `joined` reply is lost (the network drops again, which is exactly when reconnects happen, or the app dies before it saves the new token) leaves the client holding a dead token, so it comes back as a new peer and loses its slot for the rest of the session. A stable token makes every reconnect retryable, matches BRIEF 5.3 ("a reconnect token stays valid for 120 s and keeps the same peer id; clients save it in their profile dir") and works whether NetSession saves the token once or after every `joined`. Rotation's gain, a leaked token working only once, is small: tokens go only to their owner, over `wss` in production, and are never logged. Takeover makes the e2e restart (BRIEF 7.7) work even when the old socket lingers. A client closed with 4001 should not reconnect by itself, or two copies of one profile would take the seat from each other in turn.
- **The slow-consumer limit is also checked on every frame received.** Both WebSocket layers answer WebSocket pings themselves, outside the relay's rate limit, so a client that floods pings and never reads would otherwise grow its socket's backlog without bound. On every incoming frame the relay closes a connection whose unsent output is over 1 MiB (4003, a drop), the same rule it applies before each send. *Alternative:* count WebSocket pings in the message rate limit. *Reason:* BRIEF's 60 a second counts messages, and the backlog rule bounds memory directly in both layers with one check in the core.
- **`node src/main.ts` refuses unknown options, and a blank `PORT` means the default.** Options are parsed by a pure function (`src/options.ts`) with unit tests. Flags are `--name=value` and win over the environment. A typo such as `--prot=0` or `--port 0` exits with code 1 and the usage text instead of silently binding port 8787. A blank `PORT` or `HOST` (for example `PORT=` in a shell or compose file) counts as unset, where `Number("")` used to turn it into port 0, a random port.
- **The host drop and `host_left`.** A host drop sends `peer_left {peer: 1, reason: "dropped"}`, and the room is held 120 s. Messages to the host are dropped while it's away, and new peers may still join. `host_left` carries a `reason`: `left` (explicit leave), `timeout` (the host's token expired) or `expired` (the 4 h lifetime; the host gets it too). After `host_left`, peers stay connected outside any room and may create or join again on the same socket.
- **`joined.peers` lists the connected peers.** A host that reconnects after a drop learns who is still there, including peers that joined while it was away, whose `peer_joined` it missed. Nothing sent while a peer was away is replayed; NetSession resends state on `rejoin` (OWNERSHIP NET6).
- **`d` is forwarded byte for byte.** After `JSON.parse` validates the message, `src/json_span.ts` finds the raw text of the top-level `d`, and the relay sends `{"t":"msg","from":N,"d":<raw>}`. *Alternative:* `JSON.stringify(parsed.d)`. *Reason:* "never looks inside d" also means "never rewrites it". Integers above 2^53 (64-bit seeds) and spellings like `1.0` survive. It's also cheaper than re-encoding a 16 KB snapshot ten times a second.
- **Non-hosts may only address the host.** A client's `msg` with `to` other than 1 (including `to: 0`) gets `bad_request` and is dropped. A `msg` to a peer that isn't connected, or to the sender itself, is dropped silently, because a peer leaving is a normal race.
- **Slow consumers are closed.** A connection with more than 1 MiB of unsent output is closed with 4003 and treated as a drop. *Reason:* one stalled client must not grow the relay's memory without bound while the host streams 10 Hz snapshots.
- **Logging and `/health`.** Logs carry only room serial numbers and counts, never codes, tokens or payloads (a unit test checks this). `/health` returns `{status, proto, impl, uptime_s, rooms, connections, peers, held}`, with 503 `closing` during shutdown. A shutdown closes every socket with 1001. The entry prints `WATTLANDS_RELAY <ws url>` once it listens, so harnesses can start it on `PORT=0`. It binds all interfaces by default (dual stack, so `ws://localhost` works whether localhost resolves to ::1 or 127.0.0.1).
- **TypeScript without a toolchain.** The sources use erasable syntax only (no enums, namespaces or parameter properties; type imports use `import type`), with explicit `.ts` import extensions, so Node runs them directly. `package.json` scripts pass `--experimental-strip-types` for Node 22.12–22.17. `tsconfig.json` is for editors. A scratch check with TypeScript 6.0.3, `@types/node` 26.6.4 and `@types/ws` 8.18.2 (`strict`, `erasableSyntaxOnly`, `verbatimModuleSyntax`) passed with no errors. TypeScript isn't a dependency.
- **Tests are `.test.mjs` files that import the `.ts` sources, and their helpers live in `testkit/`.** `tools/lib/run_tests.mjs` detects Node suites by `.js`, `.mjs` and `.cjs` names, and `node --test` runs every file under `test/`. Without `npm ci`, the `ws` halves are skipped with a reason, so the lead's full run stays green on a fresh checkout. CI sets `RELAY_REQUIRE_WS=1` after `npm ci`, so the skip becomes a failure there.
- **The Docker image.** It is `node:24-alpine` (LTS, type stripping on by default), runs as user `node` with root-owned read-only files, runs `npm ci --omit=dev` only when `package-lock.json` exists, and has a `HEALTHCHECK` that uses Node's `fetch` against `/health` (no curl in the image). Built locally on 2026-10-21 with Docker 29.9.1 (Node 24.22.0 in the image). The container answered `/health` with `impl: "ws"`, served a create, join and msg smoke test, reported `healthy`, and exited 0 on `docker stop` (SIGTERM shutdown). The hardening review rebuilt it after its fixes (Node 24 in the image, `ws` layer): `/health` answered, a create, join, msg and same-token reconnect smoke test passed, it reported `healthy` and exited 0 on `docker stop`. The image was never pushed.
- **Caps on sockets, rooms and room creates, with defaults for a small public relay (2026-11-02).** 500 sockets (64 per IP address), 200 rooms (8 per address, counted by the address the host created the room from, held rooms included), 10 creates a minute per address, and 10 s for a valid `hello`. Each is an option (`--max-connections`, `--max-connections-per-ip`, `--max-rooms`, `--max-rooms-per-ip`, `--room-creates-per-min`, `--hello-timeout`, with `RELAY_*` variables) and 0 turns it off. The server asks `Relay.admit(ip)` before the WebSocket handshake and answers 503 (relay full) or 429 (address full) with `Retry-After: 30`, so a refused socket costs no WebSocket state; `Relay.open()` asks again and closes with 1013, in case a socket slips past. A `create` over a room cap or the create rate gets `rate_limited` and the socket stays open. A `join`, a rejoin and a host reclaiming its room with its token touch none of them: only `create` does, and the existing join limit still covers joins. When a cap is about to refuse, the relay first sweeps expired rooms, so a late sweep never refuses a create. A socket that sends no valid `hello` within the deadline is closed with 4000 (reason `no hello`); `ping` is allowed before `hello`, so it can't keep one open. The log gets one line a minute with the counts (no addresses, codes or the word `rate_limited`, which the end-to-end harness scans for). *Alternatives:* caps only on the total, a connection limit in a proxy, or a 4004 close code for the hello deadline. *Reason:* the relay is the one thing a stranger can reach, and every limit was per socket or per message, so one client could hold unbounded memory with many sockets or many rooms. The per-address numbers leave room for a venue (eight rooms of eight riders) and for eight riders behind one router, which needs one room, eight sockets and seven joins. Closing with the existing 4000 and refusing creates with the existing `rate_limited` adds nothing to the protocol or to any client. The defaults fit 256 MB (500 sockets can each hold 1 MiB of unsent output before the slow-consumer close, so more would not).
- **Only a message to the relay is activity (2026-11-02).** `onActivity` (any frame, WebSocket ping and pong included) still runs the slow-consumer check, but no longer resets the idle timer; `onText` and `onBinary` do. *Alternative:* keep counting WebSocket pings. *Reason:* `ws` and the built-in layer answer WebSocket pings on their own, so a socket that does nothing but answer them (a proxy's keep-alive, a script) held a connection slot forever. The app's `RelayTransport` sends a relay `ping` message every 15 s against the 60 s timeout, so a rider is unaffected (tests run both: a client that sends WebSocket pings only is closed at 60 s, and one that sends the relay `ping` every 15 s for three minutes stays).
- **`RELAY_TRUST_PROXY` reads the entry the nearest proxy appended (2026-11-02).** `1` (or `true`, `yes`) takes the last `X-Forwarded-For` entry, a number n the n-th from the right (an absent header or fewer entries falls back to the socket address), and `fly` takes `Fly-Client-IP`, which only that mode reads: behind Render or any proxy that doesn't overwrite it, a client could send its own. Any other value is an error at start. Entries longer than an IPv6 address are not used. `fly.toml` sets `fly` and `render.yaml` sets `1`. *Alternative:* the first entry, as before. *Reason:* a proxy appends the address it saw, so only the right end is the proxy's word; the left end is whatever the client sent, and a client could choose its own join, socket and room keys. Whether Render's proxy chain needs 1 or 2 is not confirmed from here; the README gives a two-connection check to run after deploying.
- **`/health` stays a loop over the rooms.** It counts seats in at most `maxRooms` rooms (200 by default), so it needs no cache and tests see fresh numbers; it answers at the connection cap because it isn't a WebSocket. A test pins its keys to counts only.
