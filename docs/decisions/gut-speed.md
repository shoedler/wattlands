# Decisions: gut-speed

## 2026-11-12: Tests that read the same whole session play it once

- **Decision:** where several tests of one script each played the same whole session and only read it, the script plays it once and every test reads the shared result.
  - `TestGameSessionSuite.shared_session()` does this for the game session suites: the first call with a set of flags plays the session, every call gets a deep copy of its report, and its report and FIT files stay until `after_all`, or until GUT frees the script when a suite's `after_all()` skips `super()`. A play that failed (a failed assert or an unhandled error while it ran) fails every test that asks for it, not only the one that played it. `tests/lib/test_game_session_suite.gd` holds it to all of that on the platform's own `_template` game, so no game's change can break it.
  - Rules-level suites keep a per-script cache of played games (`_played` in `test_tank_results.gd`, `_session` in `test_tank_game.gd`, `_real_wave` in `test_siege_session_audio.gd`). They are strictly read-only: the Tank caches check on every later read that the game is still as it was played (its snapshot, results, stats, progress and the sinks), and a last test in each script checks it once more. A test that writes writes into a copy: the real-session `apply_progress` test applies into a deep copy of crew 1's progress. Siege's wave keeps plain copies only and frees its game and view once the wave is played, so nothing goes on processing on wall time in the frames GUT yields between tests.
  - A test that changes what it plays (a seat move, an applied progress into the game's own store, more time after the end) plays its own.
- **What changed in the inputs.** The assertions and tolerances are the same; some tests now read a session played with other inputs than before:
  - `test_tank_session.gd`: the toasts test reads the three-human drill at seed 2 (was 4), the hash test compares two runs of the two-human drill at seed 5 (was 9), and the solo Ashfall Road snapshots test reads seed 1 (was 2), the session the zero-input test reads.
  - `test_tank_roam.gd`: the patrol test plays seeds 1 to 4 (was 1 to 8); those four spawn 23 far patrols and 7 near threats, at least twice what it asks for.
  - `test_tank_results.gd`: the XP test and the real-session progress test read crews that rode 300 kJ plus 10 per slot (was 420 kJ); the XP formula is checked the same way.
  - `test_tank_game.gd`: the bands test reads sessions played with 2.0 s of cool-down (was 1.0 s). It checks only the phases before the cool-down, so the extra second changes nothing it reads; its solo rider also carries the 420 kJ of the results test, which bands don't read.
  - `test_strava_client.gd`: the three offline tests wait 0.25 s for a request to a closed loopback port (was 1.5 s). The port refuses at once, so the timeout only bounds a machine that doesn't.
- **Alternatives:** play everything once in `before_all` (its time drops out of the JUnit per-test times, which would hide the cost rather than cut it, and a single test run alone would still pay for all of it); share across scripts with a static cache (`strict` runs every script in one process, and a cache that outlives a script is the kind of cross-file state it exists to catch); trust each test to leave a shared game alone (the first test that writes into one makes the rest order-dependent without failing).
- **Reason:** `tools/gate fast` runs the whole GUT suite, and a handful of tests that replayed the same 30-minute mission were a large part of it.

## 2026-11-12: Tests that only repeated a pinned scenario or a matrix row are gone

- **Decision:** remove the tests that played the same session with the same rider and checked a subset of what another check already holds:
  - `test_workout_sims.gd`: every built-in session graded A or better, the VO2 latch test, and the sample .zwo plays. `tests/scenarios/workout/test_workout_sessions.gd` plays every built-in session with the same compliant rider and a bot and checks the grade, the warm-up limits on every tick, that no duration limit latches, and time in band, but for the human row only; the removed test held the bot's row to 90 percent too. A new `test_the_bot_rides_e2e_in_band_too` holds the bot's row in e2e (one short play); the bot's row in the other five sessions is no longer checked. `tests/scenarios/workout/test_zwo_import.gd` plays the sample .zwo to the end inside its clamps.
  - `test_tank_session.gd`: a crew of 4 plays Ashfall Road with zero input. The tank matrix's `s1_c4_seed1` to `s1_c4_seed3` (row S1) play exactly that and check the outcome, the 13 laps, the snapshot budget and T7, the arc rider's load pattern.
  - `test_tank_sessions.gd`: the score falls with compliance 100, 85 and 70, which played the rules rig directly. The matrix's T5 checks the same order through the sim runner over `s1_c3` and `s3_c3_c85`/`s3_c3_c70` (rows S1 and S3), seeds 1 to 3.
- **What that costs.** The two Tank checks are now only in the sim matrix (`tools/gate matrix --game=tank`). A Tank branch runs it before it reports; a platform branch doesn't, so a platform change that breaks either shows at the next checkpoint's matrix, not in `fast`.
- **Alternatives:** keep them on a shorter content (they would no longer check what their names say).
- **Reason:** the scenario tests run in the same gates; the matrix runs before a tank branch reports and at every checkpoint, with the BRIEF 4.6 checkers.

## 2026-11-12: The audio scorecard's verdict cache fails closed and says what it did

- **Decision:** `tools/audio/lib/verdict_cache.mjs` records reads through five fs functions (`readFileSync`, `existsSync`, `readdirSync` one level, `statSync`, `lstatSync`) and treats every other function of `node:fs` and `node:fs/promises`, their `.native` twins and the stream classes as unrecorded: a scoring run that uses one stores nothing. `scorecard_banks.test.mjs` prints one line per bank, `scored` or `cached verdict, inputs unchanged`, and prunes entries that match no bank on disk or older scoring code. `tools/audio/README.md` says how to score every bank afresh.
- **Alternatives:** a deny-list of the read functions in use today (a later `globSync`, `realpathSync` or promises read would go unrecorded and a stale pass would be kept); hashing every file under `assets/` (slower than scoring a small bank, and still blind to a read outside it).
- **Reason:** a cache that keeps a pass it shouldn't hides a failing bank from the gate; one that misses only costs time.
