# Decisions: rides (recorder, FIT, Strava, mock Strava, fit_check)

Short ADRs for `addons/wattlands/rides/`, `server/mock_strava/` and `tools/fit_check/` (BRIEF 3.8, 7.1, 7.5).

- **2026-10-21: Records are sample-and-hold at whole seconds; totals are integrated.** Record k is stamped at UTC start + k and holds the latest values fed at or before that second. Work, distance (from the reported speed) and time-weighted cadence and speed are integrated between `record()` calls with the held values; averages are over elapsed time; maxima are the largest values fed. *Alternatives:* averaging every sample inside each second; work as the sum of record powers. *Reason:* the recorder gets ~1 Hz trainer samples with jitter or 20 Hz ticks, and both give one record per second and the same totals; integration over platform time is exact for the piecewise-constant feed and independent of the feed rate.
- **2026-10-21: Pauses stop the FIT timer, not the records.** `set_timer_running(false)` writes a timer stop_all event; paused time counts in elapsed time and not in timer time; records continue (the trainer still runs on platform time). *Alternative:* no records while paused. *Reason:* BRIEF 7.5 checks one record per second over the ride, and a paused rider may still pedal.
- **2026-10-21: A lap at the instant the current lap started renames it.** `start()` opens the first lap; each `lap(label, t)` closes it at t and opens a new one, unless no time has passed in the current lap. Expected laps = lap() calls after the start instant + 1, which equals OWNERSHIP FIT1's formula (lap-true phases + lap_markers + 1 for the cool-down) when the first phase is lap-true (Workout, Siege, Tank and Fishing all start that way); a lap-false first phase adds the opening lap. *Alternative:* a zero-length lap. *Reason:* LocalRider laps phase 0 at the ride's start, and zero-length laps are noise in Strava.
- **2026-10-21: Lap names travel in one developer field.** The FIT lap message has no name field, so the encoder declares developer data (index 0, a fixed application id) with field 0 `lap_name` (string, 32 bytes) and adds it to every lap. *Alternatives:* workout_step messages linked by `wkt_step_index`; no names. *Reason:* `PlanPhase.label` is documented as the FIT lap name; a developer field is the standard way, Garmin's SDK decodes it, and Strava ignores it.
- **2026-10-21: FIT header: protocol byte 0x20 and profile version 2140 (21.40).** *Alternative:* the SDK's 21.218 encoding (21218). *Reason:* 0x20 is protocol 2.0 in the FIT header's nibble encoding; every field we write exists in profile 21.40, and the major*100+minor encoding is read the same way by every decoder.
- **2026-10-21: Fixed local message types, each definition written once.** file_id 0, developer_data_id 1, field_description 2, device_info 3, event 4, record 5, lap 6, session 7, activity 8; little endian; no compressed timestamps. Messages are written in time order (a lap before the records of its end second), then the last timer stop, the last lap, the session and the activity. *Reason:* simplest valid layout; Garmin's SDK decodes it with zero errors.
- **2026-10-21: `save()` never overwrites; `save_as()` writes an exact path.** Two rides that start in the same UTC second get `_2`, `_3` stems. `save_as(path)` (additive) exists for GameSimRunner's `<report dir>/fit/<report stem>_slot<n>.fit`. The JSON summary always sits next to the FIT with the same stem.
- **2026-10-21: The ride UUID comes from the OS's secure random bytes.** `RideRecorder.new_uuid()` uses `Crypto.generate_random_bytes` (RFC 4122 v4). *Alternative:* the seeded RNG. *Reason:* it is an identifier for Strava's `external_id`, not simulation state; it never enters a rule. Callers that need a deterministic id (sim reports) set `ride_id` before `start()`.
- **2026-10-21: HTTP through `HTTPRequest` with redirects followed by hand.** Every request goes through `Locks.network_allows()`; `max_redirects` is 0 and the authorize fetch follows `Location` itself, checking each hop, so a loopback mock can't bounce the client off loopback. After a response the coroutine resumes on the next frame, outside the HTTPRequest's signal, so callers may free the client at once.
- **2026-10-21: Token policy.** Refresh when the access token has less than 10 minutes left and once on a 401; always store the refresh token Strava returns. A 400 from the refresh grant (revoked on strava.com) clears the tokens and reports `error`/`reauthorize`, keeping the client id and secret; 401, 429, 5xx and offline keep the tokens. The client's clock is the system clock (injectable for tests); this is I/O, never the sim path.
- **2026-10-21: Disconnect deletes the secret and tokens even if the revoke fails.** The client id stays in `strava.json` for a reconnect; state detail `revoke_failed` tells the UI. *Reason:* the player asked to disconnect; leaving tokens behind would be worse than an unrevoked grant they can remove on strava.com.
- **2026-10-21: Revoke falls back to deauthorize.** Disconnect calls POST <oauth base>/revoke with HTTP Basic client id/secret and the refresh token as BRIEF 3.8 says; if that endpoint answers 404 or 405 it calls POST <oauth base>/deauthorize (Strava's long-documented endpoint) with the access token in the Authorization header. *Reason:* neither endpoint can be tried against the real Strava in this run; the fallback keeps Disconnect revoking whichever one Strava serves. The mock serves both.
- **2026-10-21: Queue semantics.** Kept in `rides/upload_queue.json`: offline, 401 after a refresh, 429 after the retries, 5xx and processing timeouts (with the upload id, so a retry polls instead of uploading again). Dropped and marked `failed` in the ride's JSON: other 4xx and Strava processing errors (retrying can't fix them) and entries that failed 8 times. Duplicates count as uploaded. The queue never holds a token or the secret. Retried at launch (once connected) and after every connect.
- **2026-10-21: 429 backoff.** `Retry-After` when present, else 15 s doubling per retry (capped at 120 s), at most 3 retries per request; polling backs off the same way. *Reason:* Strava sends usage headers rather than `Retry-After`; three retries spread over ~2 minutes stay inside its 15-minute window without stalling the results screen forever.
- **2026-10-21: `--strava-base=<root>` maps to `<root>/api/v3` and `<root>/oauth`.** WlRides reads it with `CmdLine` before falling back to `Settings.strava_api_base()`/`strava_oauth_base()`, so the mapping is the same whatever Settings does with the flag. The mock serves both trees under one root.
- **2026-10-21: Auto-upload rides on `EventBus.ride_saved`.** `WlRides.save_ride(recorder)` (additive) saves and emits `ride_saved`; WlRides uploads every saved ride without a prompt when the profile's `strava_auto_upload` or `--strava-auto-upload` is set, and queues it until connected. An uploaded ride is never sent twice (its JSON records the upload), so a results screen that also calls `upload()` can't double it.
- **2026-10-21: `--strava-client-id` and `--strava-client-secret` connect at start.** For scripted peers (e2e), WlRides runs the loopback connect deferred from `_ready`, then retries the queue.
- **2026-10-21: The mock rotates refresh tokens strictly.** Every refresh issues a new refresh token and the previous one stops working at once. *Reason:* stricter than Strava (which may return the same token), so a client that keeps an old token fails the tests.
- **2026-10-21: `fit_check` compares each FIT with its summary.** When `<stem>.json` next to the FIT is a RideRecorder summary, record and lap counts and session totals must match (BRIEF 7.5 "session totals equal to the recorder's"). One record per second is checked as floor(elapsed) + 1 records within 1 % (at least 2).
- **2026-10-21: The fallback decoder contract is a flag-and-JSON interface.** `tools/godot.sh --headless --path <repo> -s res://tools/fit_decode/decode.gd -- --json-out=<path> --file=<path>...` writing the JSON in `tools/fit_check/README.md`; `check.mjs` runs the same checks on it. qa builds the decoder; `tools/fit_check/testdata/fake_decode.mjs` is a reference implementation of the contract.
