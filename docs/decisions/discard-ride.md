# Decisions: discard-ride

- **2026-10-31: Discard the ride drops the recorder and skips `_apply_results` on the rider's machine, and ends the session on End/Leave's path.** Decision: `AppSessionScreen.discard_ride()` calls the additive `GameHost.discard_own_ride()`, then the unchanged `end_ride()`, then goes to the title. `discard_own_ride()` sets `LocalRider.recorder` to null, the state a rider set up with `record: false` is in, so `finish_ride()` writes nothing on any later path (the session's end, an app quit, a trainer switch, a new setup) and `ride_saved` never fires, which is what starts an upload. `_apply_results` returns early, so there is no `apply_progress`, no `progress.save()`, and no `results_ready` or `unlocks_ready`. *Alternatives:* a `LocalRider.discard_ride()` method (`local_rider.gd` is safety-pinned, and the public field is enough); delete the FIT after saving it (`ride_saved` would already have started the upload); a `discard` flag on `end_session` (a changed signature, and three other callers). *Reason:* no trainer code changes: no new call reaches the governor, and the screen hands the rider back to menu time when it leaves, as End does. The recorder holds a ride in memory and writes only on save, so no partial or crash-safe file exists to remove.
- **2026-10-31: A host that discards leaves with `WlNetSession.leave_when_flushed()`, and a client applies results waiting in its inbox when the host leaves.** Decision: End keeps a host in the room until Continue on the results screen; a discard goes straight to the title, so it has to leave at once. `leave()` clears the send budget's queue, which can hold the results, so `leave_when_flushed()` waits for the queue in `poll()` (a new room or an offline start leaves first). On the client a leave can then arrive in the same poll as the results, while `refused` fires at once and the inbox drains only in `step()`: the session screen calls the additive `GameHost.apply_pending_results()` first. *Alternatives:* keep the session screen up for a grace period (a later trainer hand-over than End's, and a stall can still outlast it); stay in the room from the title (other screens assume no room). *Reason:* "other riders still get their results and FIT" must hold on a slow link too. The drain also helps a host that quits the app right after the results.
- **2026-10-31: On the confirm, a surge counts on "Yes, discard" only after 2 s there, and the confirm scans at 4 s or slower.** Decision: auto picks are ignored, the list's `erg_auto_confirm` and `follow_local_mode` stay off, an auto-pause holds "Keep riding" without scanning, and `DISCARD_SURGE_DWELL_S` swallows an early surge. *Alternatives:* no scanning on the confirm (a pedal-only rider could not discard, BRIEF 3.9); a third confirm. *Reason:* a surge fires up to about 1.5 s after it starts and the default scan moves every 1.6 s, so a rider surging for "Keep riding" could land on "Yes, discard" and lose the ride. A wrong pick here cannot be undone, unlike End. Keyboard and controller picks are deliberate and have no dwell.
- **2026-10-31: "Keep riding" is the ride menu's Resume, except in a panic.** Decision: it closes the overlay and resumes a pause; in a panic it returns to the panic menu, since only "Resume the trainer" leaves a panic (BRIEF 4.6.5). A panic or a pause ending closes the confirm. *Alternatives:* make it the same as Back (the words promise riding on). *Reason:* the words, and a discard menu must never resume a trainer that went safe.
