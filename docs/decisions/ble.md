# Decisions: ble (W1)

- 2026-10-21. Decision: `GdbleTransport` and `BridgeTransport` refuse every write while `WATTLANDS_NO_HW_CONTROL=1` (push_warning "hardware control locked", `operation_failed("write", ...)`), and the Python bridge refuses `write` under the same variable in its own environment. Alternatives: rely on `FtmsClient`'s lock alone. Reason: defence in depth for BRIEF 1. Under the lock `FtmsClient` never writes anyway, so nothing changes for the app; a bug above the transport still can't reach a real trainer. Scan, read and subscribe stay allowed.
- 2026-10-21. Decision: backend choice skips GDBLE only when its library isn't loaded; when GDBLE loads but reports no adapter, the bridge is tried next; the bridge is always tried, because its reachability is known only after `initialize()`. With neither, the status is `STATUS_DISCONNECTED` with the translated detail "No Bluetooth adapter found" (GDBLE loaded, no adapter) or "Bluetooth is unavailable ..." (nothing loaded or reachable), plus push_warning. Alternatives: `STATUS_ERROR`; stop after GDBLE's answer. Reason: the stub says no adapter is never an error; a PC without Bluetooth is a normal setup that plays with the mock trainer, and the bridge may work where btleplug doesn't.
- 2026-10-21. Decision: one backoff schedule for every failed link: `backoff_delay(n)` = 1, 2, 4, 8, then 15 s, for a lost link, a failed connect, a connect that takes over 20 s and a setup (FtmsClient `begin()`) that fails or takes over 30 s. It resets when the trainer is ready again. Timers advance only in `tick(dt)`; `_process(delta)` calls it unless `manual_clock` is set. Alternatives: retry only after a loss; separate first-connect logic. Reason: BRIEF 4.4 gives one schedule; a KICKR's first connect on Windows sometimes fails, and a single state machine is easier to test.
- 2026-10-21. Decision: a reconnect reuses the same `FtmsClient` (attached once per transport) and the same `FtmsTrainer` (created once per trainer address), runs `FtmsClient.begin()` again (rediscover, resubscribe, indications, Request Control, SIM flat), then emits `trainer_ready(device)` followed by the additive `reconnected(device)`. A GATT reset (GDBLE `EVENT_OVERFLOW` on notifications or `SERVICES_CHANGED`) does the same without dropping the link. Alternatives: a new device per reconnect. Reason: the governor keeps its device reference, and `reconnected` is the one hook it needs to restore its last safe mode (begin() leaves the trainer in SIM flat).
- 2026-10-21. Decision: control lost (Request Control 0x05 or Machine Status 0xFF) sets `STATUS_CONTROL_LOST` with "Another app may hold control of the trainer (Zwift, the Wahoo app). Close it, then retry.", emits the additive `control_lost(detail)` and never retries on its own; `retry_control()` runs `begin()` again when asked. Alternatives: retry with the backoff. Reason: grabbing control back every few seconds from a Zwift session the rider started on purpose would fight the other app and could change resistance under the rider.
- 2026-10-21. Decision: under the hardware lock, a setup failure keeps the read-only link (`STATUS_ERROR`, "Trainer setup failed (...). Hardware control is locked (read-only).") and stops; without the lock it drops the link and retries with backoff. Alternatives: retry in both cases. Reason: under the lock Request Control is refused by design, so a retry loop would never end.
- 2026-10-21. Decision: GDBLE events. Device signals and the manager's `device_connected`/`device_disconnected` are both connected and deduplicated, so each link change is reported exactly once (`reason` "local" after `disconnect_device()`, else "remote"; a disconnect before the link came up is a failed connect). `ble_event` is used only for unsolicited events: a non-terminal initialize failure (adapter powered off) becomes `adapter_ready(false, code)`, and the manager then re-runs `initialize()` before its next attempt. Every `start_scan()` re-announces GDBLE's discovery cache, because GDBLE deduplicates discovery over the adapter's lifetime. Alternatives: the structured events only; the legacy signals only. Reason: API_CONTRACT.md recommends device events for device work, and the legacy signals carry BRIEF 4.2's 0.5.x surface; the cache replay keeps a rescan useful.
- 2026-10-21. Decision: GDBLE device handles are held as `RefCounted` and called only through `call(&"...")`; signals are connected and disconnected through `Signal(obj, name)`. The test double's zero-argument `disconnect()` overrides `Object.disconnect` with default arguments under `@warning_ignore("native_method_override")`. Alternatives: untyped variables; a different method name in tests. Reason: `docs/deps.d/gdble.md` (the name clash); `Signal(...).disconnect` reaches Object's own method even on a fake that defines `disconnect()`.
- 2026-10-21. Decision: the bridge protocol is JSON text frames with integer request ids, `{ok, result, error}` responses, `{event}` messages and lower-case hex payloads; UUIDs expanded and lower case on the wire. The bridge binds to 127.0.0.1 only, serves one client at a time, runs requests in order (scans in the background) and releases the trainer when the app disconnects. `BridgeTransport` accepts loopback URLs only and has open (3 s) and request (10 s, connect 25 s) timeouts on `tick(dt)`. Alternatives: binary frames; base64. Reason: readable logs, trivial on both sides (`PackedByteArray.hex_encode`, `bytes.hex`), and nothing ever leaves the machine.
- 2026-10-21. Decision: the probe and the bridge tests use their own Python FTMS parsers and `tools/trainer_bridge/tests/vectors_local.json`, transcribed from BRIEF 4.3, until trainer-core's `tests/vectors/ftms.json` lands; a tolerant reader then checks every Indoor Bike Data case in that file whose field names it can map. The bridge itself forwards raw bytes and never parses. Alternatives: wait for the shared file. Reason: W1 builders run in parallel; the GDScript `FtmsCodec` stays the codec the app uses.
- 2026-10-21. Decision: `bleak` is imported lazily and only by `BleakBackend`; the server, the probe and the parsers are tested against a fake backend. Here bleak could not be installed: Python 3.15.0 is the only interpreter, the `winrt-*` wheels bleak 3.0.2 needs don't exist for it, and building them needs Microsoft C++ Build Tools (BRIEF 2: treat Python as absent for those parts). websockets 17.3 and PyInstaller 6.22.3 installed fine. The probe never ran against hardware in this run. Alternatives: download another Python (BRIEF 1 forbids it). Reason: the proxy, the protocol and the probe's safety rules are still fully tested; only the bleak calls themselves are unverified.
- 2026-10-21. Decision: the app doesn't start the bridge itself yet; a user starts `trainer_bridge serve` (or the PyInstaller exe) and the manager finds it on its next `start()`. Alternatives: `OS.create_process` from the manager when GDBLE has no adapter. Reason: P1 asks for the bridge and the spec; launching a child process belongs with app settings (a path to the exe and an opt-in), so it is a backlog note.
- 2026-10-21. Decision: status details are translated text from `content/strings/ble.csv` (`BLE_STATUS_*`, filled with `String.format`), and JSON from the bridge or the last-device file is parsed with `JSON.new().parse()`. Alternatives: English literals; `JSON.parse_string()`. Reason: BRIEF 6 strings rule; `parse_string` logs an engine error on bad input, which GUT counts as a failure and which bad input from an external process shouldn't cause.
