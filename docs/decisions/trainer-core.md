# Decisions: trainer-core (W1)

Short ADRs for `addons/wattlands/trainer/` (FtmsCodec, FtmsClient, FtmsTrainer, MockTrainer), `tests/trainer/` and `tests/vectors/ftms.json` (BRIEF 1, 4.1-4.6).

- 2026-10-21. Decision: `FtmsCodec` is a static, pure class; parsers return a Dictionary of named fields, or `{}` after a `push_error` when bytes are short or malformed. Scaled values decode as `raw / 10^n` (3050 -> 30.5 exactly as JSON writes it), unscaled ones as ints. Alternatives: typed record classes; returning `{ok, error}`. Reason: Dictionaries cross into `bike_data` signals, reports and JSON vectors unchanged, and dividing by an exact power of ten gives the same double in GDScript, Python and JS, so the golden vectors compare exactly.
- 2026-10-21. Decision: encoders round half away from zero, then clamp to the field's range (sint16, uint8 ...); Set Target Power clamps to 0..32767 (never negative); NaN encodes as 0. Safety limits (grade -10..+16 %, the ERG ceilings) stay in the governor, not the codec. Alternatives: banker's rounding; clamping to KICKR limits in the codec. Reason: one rule every language can reproduce (the vectors pin it with exact binary ties such as 0.125 % -> 13 and -0.125 % -> -13), and BRIEF 4.6 keeps every safety rule in one place.
- 2026-10-21. Decision: Indoor Bike Data reassembly merges parts until one has More Data clear; a part that repeats a field already pending flushes the pending record as incomplete (`more_data` true), and 8 parts flush it too. A malformed part is dropped without discarding the pending record. Alternatives: drop incomplete records; reset on every error. Reason: some FTMS devices set More Data on every notification; with the repeat rule they still deliver a record per notification (one notification late) instead of none.
- 2026-10-21. Decision: `tests/vectors/ftms.json` holds `encode`, `parse` and `assemble` lists with lower-case hex and a `_doc` array that defines every key, op, rounding and error rule. A parse case is either `valid: true` with the complete expected output, or `valid: false`. Alternatives: one file per kind; only valid cases. Reason: ble's Python tests reuse the file; a self-describing format and explicit malformed cases let them reach byte parity without reading GDScript. The vectors were cross-checked with an independent JS implementation before commit.
- 2026-10-21. Decision: `FtmsClient` waits `SUBSCRIBE_SETTLE_S` (0.25 s) after subscribing (0x2AD2, 0x2ADA, then 0x2AD9 last) before Request Control. Alternatives: write at once. Reason: `BleTransport` has no subscribe acknowledgement, btleplug writes the CCCD asynchronously, and an indication missed because the CCCD write lost the race would cost a 2 s timeout.
- 2026-10-21. Decision: reads use the control point's timing (2 s, two retries) one at a time; Feature is required, the ranges and Device Information are optional and keep KICKR defaults (0..1800 W, 0..100 resistance). Alternatives: fail on any missing read. Reason: KICKR firmware versions differ in what they expose, and the defaults are the trainer the brief targets.
- 2026-10-21. Decision: under the hardware lock the flow stops after subscribing: state `read_only`, a `hardware control locked` warning and `client_ready`, so telemetry flows; `is_ready()` stays false and every write (`write_control`, `request_control`, the flow's own Request Control and SIM flat) is refused and logged. The lock is checked at entry and again right before the transport write. Alternatives: fail the flow; never emit `client_ready`. Reason: BRIEF 1 allows scan, read and subscribe; a read-only client keeps the probe-style data path testable, and the second check covers a lock set while writes were queued.
- 2026-10-21. Decision: control-flow tests use `tests/trainer/unlocked_ftms_client.gd`, a test-only subclass that overrides `_is_hw_locked()` for that instance and only talks to the fake KICKR. The process keeps `WATTLANDS_NO_HW_CONTROL=1` throughout; lock tests use the real `FtmsClient` with the variable set to `1` explicitly and restored. Alternatives: set the variable to `0` around each test. Reason: no test ever lifts the process-wide lock (BRIEF 4.6.10), and the production class has no bypass: it always reads the environment.
- 2026-10-21. Decision: queued (unsent) Set Target Resistance/Power/Simulation writes are replaced by a newer write with the same op code; Request Control, Reset, Start and Stop are never coalesced. Alternatives: plain FIFO. Reason: BRIEF 4.5's "drop superseded commands; always send the newest", without ever reordering or dropping a state change.
- 2026-10-21. Decision: a control-point write still unanswered after its two retries (6 s) emits `failed()` and drops the queue; result 0x05 or Machine Status 0xFF emits `control_lost("another app may hold control")`; `request_control()` (added) re-requests control and returns to ready through SIM flat. Alternatives: skip the timed-out write and continue. Reason: three silent attempts mean the link is gone, and the connection manager's reconnect (BRIEF 4.4) is the right recovery.
- 2026-10-21. Decision: Cycling Power fallback is active when the Feature lacks power measurement (machine bit 14) and the trainer offers 0x1818/0x2A63; the latest CPS power fills `power_w` (`power_source: "cps"`, `TrainerSample.POWER_FROM_CPS`) into bike data records that lack it. Alternatives: emit separate CPS samples. Reason: one sample stream per device keeps LocalRider unchanged.
- 2026-10-21. Decision: a client inside the tree ticks itself from `_process` (PROCESS_MODE_ALWAYS); a client outside the tree is ticked by `FtmsTrainer.tick(dt)`. Alternatives: only `_process`; only the trainer. Reason: the connection manager runs the flow before an `FtmsTrainer` exists, while tests and headless runs need deterministic ticks.
- 2026-10-21. Decision: `FtmsTrainer` does not estimate cadence. A record without cadence becomes a sample without `HAS_CADENCE`; `CadenceEstimator` (trainer-control), which LocalRider runs on every sample, fills it. Alternatives: a second estimator inside FtmsTrainer. Reason: the W0 contracts put estimation in `CadenceEstimator`; two estimators would disagree.
- 2026-10-21. Decision: MockTrainer fatigue is a hard W' model: the follower holds any target while W' (Skiba, CP = FTP unless `cp_w`, W' 20 kJ unless `wprime_j`) lasts, then gives 95 % of CP until 10 % of W' has come back. Scripted profiles ignore fatigue. Alternatives: power fading with W'. Reason: time to failure is exactly W' / (P - CP) (150 % FTP fails after about 160 s, sub-CP targets never do), Workout's VO2 session never exhausts a compliant rider, and the analytic ramp-test model in BRIEF 7.4 stays valid.
- 2026-10-21. Decision: every surge lasts at least until two notifications carried it (it is extended past `for_s` if needed), no dropout touches a surge or the 10 s before one, and gaps never chain. Alternatives: align surges to the notification schedule. Reason: docs/OWNERSHIP.md C30: ten surges must give ten ERG surge gestures; the test runs five seeds with and without dropouts.
- 2026-10-21. Decision: `band` uses a first-order lag (tau 2 s) and an Ornstein-Uhlenbeck noise (sd 0.6 rpm, tau 4 s) clamped to +-1.5 rpm, so samples (rounded to 0.5 rpm) stay within 2 rpm of centre + offset. Alternatives: white noise. Reason: smooth like a rider and bounded, so Fishing's +-18 rpm offsets hold 10 rpm outside a 16 rpm band.
- 2026-10-21. Decision: `cadence_drop` rpm 0 means the rider stops (0 W); any other rpm leaves power to the ERG follower. `at_phase` counts `after_s` from entering the phase and re-arms if the phase ends first; `at_target_pct` compares the commanded ERG target (what the governor applied, after the unverified factor) and ignores SIM. Each instance fires once; overlapping drops use the lowest rpm. Alternatives: drops that also cut power. Reason: ERG holds power at low cadence on a real trainer; the rescue rule's cadence branch is what these scenarios exercise.
- 2026-10-21. Decision: the follower sprints outside ERG at >= 120 % FTP: cadence +10 % (not for `band` riders) and a reported cadence that lags its fall for 5 s (tau 1.5 s); the ERG flywheel speed follows the true cadence, SIM speed comes from a `SpeedModel` (rider `weight_kg` + 8 kg) at the commanded grade and wind, seeded from the flywheel speed on entry. Alternatives: speed from cadence in SIM too. Reason: BRIEF 4.5's "cadence ... lags after sprints" and 3.11's speed model, without false ERG surge gestures (the lift never applies in ERG).
- 2026-10-21. Decision: test doubles (`fake_kickr_transport.gd`, `unlocked_ftms_client.gd`) have no `class_name` and are loaded by path. Alternatives: `FakeBleTransport`. Reason: other W1 modules may write doubles with the same obvious names; script classes are global.
- 2026-10-21 (hardening, supersedes the coalescing entry above). Decision: a new Set Target Resistance/Power/Simulation write replaces only the queue's last (unsent) write, and only when that write and the one going out just before it (queued or in flight) have the same op code; otherwise it is appended. Alternatives: replace a same-op write anywhere in the queue (the first W1 rule); plain FIFO. Reason: the first rule could reorder commands ([ERG 200, SIM 0] + ERG 180 sent ERG 180 before SIM 0, leaving the trainer in SIM while the controller meant ERG) and could drop the entry write of a ramped mode switch (SIM grade 0, the low ERG entry, BRIEF 4.5). Tail-only replacement inside a same-op run keeps the order and every mode's first write, and still drops superseded targets.
- 2026-10-21 (hardening). Decision: service discovery that has not answered after `FtmsClient.DISCOVER_TIMEOUT_S` (10 s) fails the flow with `failed("service discovery timed out after 10 s")`. Alternatives: wait forever; retry discovery inside the client. Reason: without it a lost `services_discovered` left the client in `discovering` with no signal, so the connection manager never reconnected; recovery belongs to its backoff (BRIEF 4.4).
- 2026-10-21 (hardening). Decision: `MockTrainer.restart_profile()` restarts profile time (at_s drops, surges, ramp, intervals) without touching the rider, the commanded state or the notification schedule; `profile_time_s()` reports it. Alternatives: rebuild the mock at session start; count at_s from the first phase. Reason: with `--mock-trainer` the TrainerService creates the mock at launch and ticks it through the menus, so at_s and surges would otherwise count menu time; rebuilding would swap the device under the governor.
