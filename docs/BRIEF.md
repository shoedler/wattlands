# Wattlands: platform build brief (Godot + Wahoo KICKR CORE)

You are the lead engineer and orchestrator for a one-shot build of the Wattlands platform. Wattlands is a multiplayer fitness party app for the Wahoo KICKR CORE smart trainer, built in Godot. It's one app that hosts several games. This run builds everything the games share: the app shell, the trainer stack and its safety governor, multiplayer, rides with FIT export and Strava upload, the Game SDK, the 2D and 3D presentation kits, the art pipeline, and one reference game, Workout, that proves the whole stack end to end.

Three games come later, one session each, from their own briefs: `docs/games/siege.md` (Generator Siege), `docs/games/tank.md` (Tank Crew) and `docs/games/fishing.md` (Big Game Fishing). Don't build them. Do build every platform piece they rely on: read all three game briefs in W0 and make sure the SDK, kits and tools cover every call, helper and command they cite.

Run the work as a sequence of dynamic workflows with many parallel subagents (section 8). I am not available during the run: never stop to ask me anything. When something is ambiguous, choose what best serves the pillars in section 3.1, record it in docs/DECISIONS.md, and continue. Stop only when the Definition of Done (section 9) is met or the fix-round caps are reached, then give an honest final report.

## 0. Hard requirements

1. Engine: Godot 4.7.x stable (4.7.2 or a later 4.7 patch; no 4.8 pre-releases), GDScript with static typing everywhere except GDExtension classes (4.2). Primary target: Windows 10/11 desktop. Renderer: Compatibility, for modest PCs and for headless or software-rendered testing.
2. Hardware: Wahoo KICKR CORE (2018 onward, current firmware) and KICKR CORE 2, over Bluetooth LE FTMS. Use ERG mode wherever it makes a game better.
3. Input: pedaling first, plus an optional Xbox controller and light keyboard use. Solo play and hosting, including every menu, game, shop and results screen, must work with zero input through Autopilot and pedal gestures. Joining a friend's room needs only the typed code.
4. Multiplayer from the first commit: a host gets a short room code and friends type it to join. No accounts, logins or email.
5. Games: one app hosts games as modules through the Game SDK (3.6). This run ships the reference game Workout (3.7) and a template game. The platform supports both 2D pixel-art games and 3D low-poly games (3.9), and 2D art generated with the art pipeline (3.10).
6. Rides: every ride is saved as a FIT activity file, with optional upload to the rider's own Strava account (3.8).
7. Testable without hardware or live services: a mock trainer, byte-level protocol tests, headless simulation, an automated multiplayer end-to-end test, a mock Strava server and a mock fal server.

## 2. Environment bootstrap (part of W0)

- Detect the OS and shell. Godot: use `$GODOT` or `godot` on PATH; otherwise download the official Godot 4.7.2 (or later 4.7 patch) standard build for this OS from the godotengine GitHub releases. On Windows use the `_console.exe` binary. Verify that `--version` reports 4.7. If `$GODOT` is a .NET (mono) build, use it to run and test (the project stays GDScript only, never add C#); exports need the standard build's export templates of the same version.
- Run every Godot invocation through `tools/godot.sh` (`tools/godot.ps1` on Windows). The wrapper closes stdin, applies a timeout, never passes `-d`, and holds a machine-wide lock allowing at most 2 concurrent Godot processes (4 with at least 8 cores and 16 GB free RAM); a fresh import alone can use about 750 MB. A caller may take several slots at once (`--lease=<n>`, or the same lock from Node). A lease is granted atomically, never in parts, and a lease larger than the machine's cap is granted only while no other slot is held. Grants are first come, first served: each request takes a numbered ticket (exclusive-create, PID liveness, dead tickets reaped), and no slot goes to a later ticket while an earlier one waits, so a waiting multi-slot lease holds back new single-slot grants until it is served. The wait has its own timeout (default 45 min, `--lock-timeout=<s>`, the same in the Node helper); when it expires the caller starts nothing, prints "godot lock wait timeout" and exits 75. The end-to-end harness takes one lease for all its Godot instances (the host and two clients; the restarted client reuses the killed one's slot) and holds it for the whole run. On Linux the wrapper also sets `XDG_DATA_HOME=<worktree>/.userdata` (gitignored) so parallel worktrees don't share Godot's user directory.
- On Windows, `tools/godot.sh` also runs under Git Bash, and both wrappers share one lock that needs no `flock`: a Node helper, for example `tools/lib/godot_lock.mjs`, with exclusive-create lock files and PID liveness checks under `os.tmpdir()/wattlands-godot`. On Windows both wrappers set `APPDATA=<worktree>/.userdata`, for the same reason as `XDG_DATA_HOME` on Linux; export runs skip this, because they need the installed export templates. The timeout kills the whole process tree (`taskkill /T /F`). `.ps1` scripts target Windows PowerShell 5.1, and Node tools start them with `powershell -NoProfile -ExecutionPolicy Bypass -File`. Every tool the game briefs call (`tools/run_game_sim`, `tools/new_game`, `tools/screenshot`, `tools/run_tests`) exists under exactly that name as a bash script with a shebang, plus a `.ps1` twin, and `docs/GAME_SDK.md` shows both forms. After W0's first import, check `git status`. If the import changed tracked files (a .NET build can touch `project.godot`), decide once whether to commit or revert them and record it in DECISIONS.md, so later imports leave the tree clean.
- Never run two imports or editors on one folder. Several game instances may run from one folder once its import has finished (the end-to-end test does this).
- Run `tools/godot.sh --headless --path . --import` after adding files and before tests to refresh caches. It does not compile GDScript, so it is never a gate; section 7 has the real checks.
- Node: use the Node on PATH if it is 22.12 or newer; never download Node. The relay, the mock Strava server, the mock fal server, the art generator and the end-to-end harness must also work with zero npm dependencies if `npm install` fails (5.3). Python 3.12+ with uv or pip is optional: if bleak, websockets, PyInstaller or gdtoolkit can't be installed, treat Python as absent for those P1 parts and say so. Docker: write the Dockerfile; build it only if `docker info` succeeds.

## 3. Platform design

### 3.1 Pillars

1. The trainer is controller and force-feedback device: effort is input, resistance is output.
2. Fair for mixed fitness by default; raw power always visible.
3. Low attention: decisions every 10–30 s at most, a HUD readable from 3 m, Autopilot for everything.
4. Real training: sustained work in ERG, sprints in free simulation, warm-up and recovery built in.
5. Safe by construction: every path to the trainer goes through one safety governor.

### 3.2 Rider profile (local, no accounts)

`profile.json` (in `Paths.user_dir()`, section 6): display name, color, units (metric default), weight kg (default 75), FTP W (default 200, marked unverified until the rider types it in, finishes the FTP test, or imports it from Strava in P1), CP (= FTP), W′ J (default 20000), preferred cadence (90), drivetrain (cassette or single-speed cog), trainer difficulty % (50), haptic effects (accept on or off, intensity 0–100%, default on at 70%), safety caps (section 4.6 defaults), Autopilot default (off), Strava auto-upload (off; 3.8). Weight never leaves the machine unless the player opts in; the host receives only what the selected scaling needs.

FTP test (P1, in Settings): a 5-minute ramp-in from 50% to 65% FTP, then one-minute ERG steps that start at 65% of the current FTP and rise by 6% of that FTP per step. It runs under the governor's ramp_test profile: duration limits and the 150% cap are suspended because the test ends itself, the ceiling is min(1000 W, the trainer's Supported Power Range max), slew and floor rules still apply, and the unverified-FTP factor does not. The test ends when power < 90% of the applied target for 10 s, cadence < 50 for 5 s, or you coast, and a 3-minute cool-down at 50% FTP follows. Each one-minute step is its own 60 s ERG phase. Rescue (4.6.3) stays armed, and a rescue trigger ends the test at once: rescue's 50% FTP stands and never ramps back into a step, the best 1-minute power so far is used, and the cool-down follows. FTP = 0.75 × best 1-minute power, saved after a 10 s countdown unless `back`.

### 3.3 Effort scaling (lobby setting)

- FAIR_FTP (default): effort = P / FTP. Physics uses P_eff = (P / FTP) × 250 W for a 75 kg reference rider.
- WKG: effort = P / weight. Physics uses P_eff = (P / weight) × 75 for the same reference rider.
- RAW: actual watts, and actual weight only if the rider shared it (otherwise 75 kg). Scaling changes only how effort turns into game output; ERG targets always come from each rider's own FTP.
- Each client computes its own effort and P_eff and sends both in telemetry, so the host never needs anyone's weight.
- HUD and results always show raw W, %FTP and W/kg (W/kg only if the rider opted in).

### 3.4 Stamina is W′ balance

Implement Skiba's differential model every sim tick and show it as the stamina bar. It is a display and game-resource model; it never changes trainer targets except through section 4.6.

```
if P >= CP:  wbal -= (P - CP) * dt
else:        wbal = Wp - (Wp - wbal) * exp(-dt * (CP - P) / Wp)
clamp wbal to [0, Wp]          # Wp = W' in joules, P and CP in watts
```

### 3.5 Input, gestures and Autopilot

Actions: confirm, back, up, down, left, right, ability_1, ability_2, item, swap, shift_up, shift_down, pause, panic. Each game defines what `swap`, the abilities and `item` do (for example moving your power to the next target, or moving to the next free seat at a checkpoint).

- Keyboard: arrows or WASD move, Enter or Space confirm, Esc back, 1 and 2 abilities, F item, R swap, Q and E shift down and up, P pause, Backspace held for 1 s panic.
- Xbox controller: left stick or D-pad move, A confirm, B back, X and Y abilities, RB item, LB swap, LT and RT shift down and up, Start pause, View plus Menu together panic.
- Everything rebindable and saved to `input.cfg` in `Paths.user_dir()` (section 6). The README explains how to map Zwift Click or Zwift Play buttons to these keys with BikeControl (open source).

Pedal gestures (a GestureRecognizer, unit-tested on synthetic streams):

- `pedal_start`: cadence ≥ 40 rpm or power ≥ 30% FTP for 3 s.
- `surge` (confirm): in menus and outside ERG, power ≥ max(1.3 × its 10 s average, 10 s average + 40 W) for 1.5 s, which is two consecutive samples at about 1 Hz. Inside ERG power is held, so use flywheel speed ≥ 1.12 × its 10 s average for 1.5 s. A stricter sprint rule (≥ 1.2 × FTP) applies only where a game scores a sprint; the platform exposes it as `SprintRule`.
- `not_pedaling`: one shared detector, power < 15 W and cadence < 20 rpm. It drives `coast`, `stop_5s`, the pause on not pedaling and the governor's coasting rule (4.6.4).
- `coast` (back): `not_pedaling` for 3 s, except during ERG, where it never means back.
- `stop_5s` (pause in menus): `not_pedaling` for 5 s, solo and outside ERG only.
- Pause on not pedaling (every mode, ERG included): `not_pedaling` for 5 s pauses the rider: the ride timer (FIT timer events, moving time) and, in solo, the game clock and plan phase; 1 s of pedaling at ≥ 30 rpm resumes. In multiplayer a stopped rider pauses only their own ride timer and sees the pause symbol; the shared game clock pauses only while every human rider is paused (bots ignored). The governor's 4.6 rules run unchanged underneath.

Pedal navigation (single-switch scanning) is opt-in: Settings has a "Pedal navigation" toggle, off by default, stored in the rider profile and copied into `PlayerSlot.pedal_nav`. Off, every menu and every in-game pick list takes the keyboard and controller only: no scan highlight, no auto-confirm, no surge-to-select, no coast-to-back. On, or with Autopilot as the rider's default, focus cycles through the options every 1.6 s (configurable); `surge` picks and `coast` backs out. Every menu works this way, including the game picker, results and every game's shop. Picks shown during ERG phases auto-confirm the highlighted option after two scan cycles. While pedal navigation is on, a small live power graph (the last 5 s) with a line at the current surge threshold shows how hard to surge. Autopilot (bots and riders with it on) and the zero-input safety rules (coasting, rescue, the pause on stopping) work with it off.

Zero-touch start: on launch, auto-connect to the last trainer; holding `pedal_start` for 5 s on the title screen starts the last-played game solo with its `zero_input_content`. First run with no input: after 20 s of pedaling on the title screen, create a profile called Rider (FTP 200, unverified) and start the first-run game solo (3.6, `first_run_priority`; Workout's Easy 30 until a game with a higher priority is installed). Joining needs a code, so offer a controller on-screen keyboard; code entry ignores dashes and spaces. P1 adds a LAN discovery list and Recent rooms (a host can reclaim their previous code), both pedal-scan selectable.

Autopilot is per player, toggled in the profile or lobby. Each game defines what it automates (power routing, shop picks, aiming, casting, lanes, items) through `autopilot_intents()` (3.6). Autopilot never changes effort targets.

### 3.6 Game SDK

Games are modules inside this one Godot project. The platform (`addons/wattlands/`) owns the trainer, the safety governor, networking, rides, menus and the HUD kit. A game owns its rules, content and presentation, and changes trainer load only by asking the platform. This run builds the SDK and the reference game Workout (3.7). Generator Siege, Tank Crew and Big Game Fishing come later, one session each, from `docs/games/siege.md`, `docs/games/tank.md` and `docs/games/fishing.md`; those sessions add files only under their own paths, apart from small additive, tested `platform:` commits when a P0 item is blocked (the platform-change policy in section 6 and `CLAUDE.md`).

- Paths per game: `src/games/<id>/` (code, `game.json`, the entry script), `content/<id>/` (JSON content, `strings.csv`), `assets/<id>/` (art, audio, `art.json`), `tests/games/<id>/` and `.github/workflows/game-<id>.yml`, plus the fragments `docs/decisions/<id>.md`, `docs/credits.d/<id>.md` and `docs/changelog.d/<id>.md`. Game ids: `workout`, `siege`, `tank`, `fishing`.
- `game.json`: `id`, `title`, `summary`, `version`, `min_players`, `max_players`, `bots` (true if bots may fill slots), `presentation` (`2d` or `3d`), `pixel_base` (2D only, for example `[640, 360]`), `entry` (res path of the GameModule script), `contents` (content ids), `default_content`, `e2e_content` (about 2 minutes, for the end-to-end test), `zero_input_content` (what a solo `pedal_start` or the first run plays), `first_run_priority` (optional integer, default 0; the first run plays the registered game with the highest value, ties go to `workout`, then to the lowest id, so another game takes the first run only with a value above 0 (3.5); Workout is 0), `picker_image` (optional res path of a 16:9 card for the game picker; a missing or unreadable file logs a warning and the picker draws a generated title card, so it never invalidates the game), and the optional `options` and `player_options` below. The `GameRegistry` autoload scans `res://src/games/*/game.json` at startup, validates each file and lists the valid games in the game picker; an invalid game is hidden with a logged reason, never a crash. `_template` is never listed.
- `GameModule` (`addons/wattlands/contracts/game_module.gd`, `class_name GameModule`, extends Node; a contract frozen after W0, section 6; games extend it by class name, never by path). The platform calls:
  - `configure(ctx: GameContext)`. `ctx` holds `players: Array[PlayerSlot]` (peer id, name, slot index, the slot's session color, shape and pattern (3.9), FTP, `ftp_verified`, scaling mode, `p_eff_per_w` (P_eff per raw watt, computed by the rider's own client: 250 / FTP in FAIR_FTP, 75 / weight in WKG, 1 in RAW), `rider_mass_kg` (the scaling mode's mass for the speed model: 75 unless RAW with weight shared; 3.3, 3.11), `preferred_cadence_rpm`, `haptics_on`, Autopilot flag, `is_bot` and `options`), `content_id`, `seed`, `role` (SOLO, HOST or CLIENT), `local_peer` (this machine's rider; the host's own in HOST and SOLO), `rng` (seeded), `directives` (a DirectiveSink), `options`, `progress`, `hud` (the HUD feed, see `hud_spec`), `intents` (see `local_intents`), `roster` (the latest 5.5 roster, keyed by peer), `strings` and `events` (the EventBus).
  - `build_effort_plans() -> Dictionary`, mapping peer id to EffortPlan: the rider's plan for the whole session, an ordered list of PlanPhase {`kind`: WARMUP, WORK, RECOVERY, FREE or COOLDOWN; `mode`: ERG or SIM; for ERG `target_pct`, optional `ramp_to_pct` (a linear ramp across the phase) and optional `range_pct: [lo, hi]` (how far the game may move the target with directives during the phase; default `[target_pct, target_pct]`); for SIM `grade_source`: `flat` (0%), `course` (a `course_profile` of [distance_m, grade_pct] points that the platform follows by the rider's distance from the speed model, 3.11) or `game` (the game pushes the course grade live); `duration_s`; `lap`; `label`}. Plans may differ per rider. Phases may be marked `open_ended` when the game decides their end (a fish fight ends when the fish is landed), with `min_s` and `max_s`; the platform ends the phase at `max_s` if the game hasn't. A game may rebuild a rider's remaining plan between phases (for example when crews rotate at a checkpoint) with `ctx.directives.replan(peer, plan)`, which goes through the same validation. The PlanValidator rejects a plan whose first 300 s break the warm-up limits (4.6.8) or whose ERG phases break 4.6.1, checking `range_pct` as well as `target_pct` and taking each open-ended phase at `max_s` for the 105% cap and for time accrued above 105% and 120%, and at `min_s` for the 120 s reset, for which phases fall inside the first 300 s, and for switch spacing, then appends the 3-minute cool-down at 50% FTP and the results screen. A game never writes its own cool-down; if it emits `finished` early, the platform skips to the cool-down.
  - `sim_step(dt: float, frame: InputFrame)`: on the host or in solo play only, at a fixed `dt` of 0.05 s on the platform's sim clock. `frame.players[peer]` holds the latest Telemetry (power_w, cadence_rpm, speed_kmh, effort, p_eff_w, wbal_j, applied_target_w, clamped_by, rescue, afk, gestures, intents), and `frame.phase` holds each rider's current phase index, kind and elapsed time. For bots and Autopilot players the platform merges in the game's own `autopilot_intents()`. A game changes trainer load only through `ctx.directives`, always inside the current phase, and that rider's governor clamps every request and reports what it applied:
    - `request(peer, EffortDirective)`: an ERG target inside the phase's `range_pct` (a fish's pull moving by ±8%, a capacitor bank raising the gunner's target), a mode grade, a haptic, or a short SIM block such as a sprint. Directives work per channel: ERG target, SIM block (`mode: SIM` in an ERG phase), `mode_grade`, haptic (grade or wind) and the `crr`/`cw` factors; `course_grade` is a separate channel. A request changes only the channels whose fields it sets, and a later request on a channel replaces it and cancels that channel's pending expiry. `duration_s` applies to the channels in its own request. When it expires, only those channels revert to the plan: the ERG target to the phase's planned target, a SIM block back to ERG, and `mode_grade` and the factors to none. `duration_s` 0 means until the phase ends. A haptic lasts at most 8 s (4.6.6), whatever its `duration_s`. A SIM block inside an ERG phase (a request with `mode: SIM` there) needs 10 s ≤ `duration_s` ≤ 30 s and must start ≥ 30 s after the rider's previous ERG ↔ SIM switch (4.5). `mode_grade` is accepted only inside such a block or in a SIM phase. The DirectiveSink refuses anything else, logs the reason with `push_warning` and reports the refusal with the applied directives.
    - `course_grade(peer, grade_pct)` for `grade_source: game` (coalesced to 2 Hz and stacked by 4.6.6);
    - `end_phase(peer)` ends an `open_ended` phase once its `min_s` has passed;
    - `cadence_band(peer, lo_rpm, hi_rpm)` publishes the cadence band a game wants (fishing's tension band). The HUD's cadence widget draws it, bots and MockTrainer's band-tracking cadence policy follow it, and it never changes trainer load. A band holds across phases until the game replaces it; `cadence_band(peer, 0, 0)` clears it, and the cool-down clears every band.
  - Game options: `game.json` may declare `options` (session-wide toggles and choices with defaults, shown in the lobby and set by the host) and `player_options` (per rider, set in each rider's lobby card, for example a wave offset). Their values arrive in `ctx.options` and in each PlayerSlot's `options`. Each entry is {`id`, `type`, `default`, optional `label`}: `type` is `toggle` (bool), `int` (`min`, `max`, optional `step`, default 1) or `choice` (`choices`: [{`value`, `label`}]). `label` is a key in the game's `strings.csv` and defaults to `<ID>_OPT_<OPTION ID>` in upper case (for example `SIEGE_OPT_WAVE_OFFSET`). Each content id is shown with the key `<ID>_CONTENT_<CONTENT ID>`, or as the bare id if that key is missing. An unknown `type`, or a `default` outside its range or choices, makes the game invalid. `player_info` carries each rider's `player_options` values and `lobby_state` echoes everyone's (5.5). Per-rider progression (catch logs, unlocks, XP) lives in `ctx.progress`, a local store under `Paths.user_dir()/games/<id>/`; it never goes to the host or the relay unless the game sends a summary.
  - During the appended cool-down the platform keeps the game's view on screen and keeps calling `sim_step` with `frame.phase` kind COOLDOWN, so a game can show the ride home; directives are ignored then.
  - `autopilot_intents(peer_id) -> Array`, `on_rescue(peer_id, active: bool)` (a stagger, never a wipe) and `on_afk(peer_id, afk: bool)`.
  - `local_intents(actions: Array[StringName], gestures: Array[StringName]) -> Array` (optional) is called on every peer each tick to turn the local rider's input actions and gestures into game intents, and the game's own HUD widgets send intents with `ctx.intents.send(intent: Dictionary)`. On clients the platform batches them into `Telemetry.intents` at 5 Hz; in HOST and SOLO it puts them straight into the local rider's `frame.players[peer].intents`.
  - `snapshot() -> Dictionary` (host, 10 Hz, compact), `apply_snapshot(snapshot: Dictionary)` and `apply_event(event: Dictionary)` (clients), and optionally `client_predict(dt: float, local: Telemetry)`.
  - `int_fields() -> Dictionary` (optional): for `snapshot` and for each event type, the dotted paths of int fields, with `[]` standing for every element of an array (for example `r[][]`); `Protocol.decode()` converts them (5.5).
  - `make_view() -> Node`: the presentation root. A 2D game returns a Node2D that the platform places in a PixelViewport at `pixel_base` (3.9); a 3D game returns a Node3D. The view reads state and never changes it.
  - `hud_spec() -> HudSpec`: which HUD kit widgets show (3.9) and where, plus the game's own Control widgets. Each widget, and the banner and toast areas, sits at a named anchor (top_left, top, top_right, bottom_left, bottom, bottom_right) or, in a 2D game, at a Rect2i in art pixels that the HUD maps through the PixelViewport's integer scale and letterbox offset. Games feed the kit through `ctx.hud`: `power_band(peer, lo_w, hi_w)` (the power gauge's band in SIM phases; in ERG it shows the applied target), `teammate_status(peer, {in_band, icon, text})`, `toast(key, args)` and `banner(key, args, seconds)`. `toast` and `banner` take an optional last argument `peer` (default: every rider). Calls made on the host or in SOLO are routed: `power_band` goes to that rider's peer as a 5.5 `directive` of kind `power_band` (lo_w, hi_w; 0, 0 clears it), where that peer's power gauge and MockTrainer use it; `teammate_status` reaches every peer in the `roster` (5.5); `toast` and `banner` reach the peers they name. A call made on a client draws only on that client's HUD.
  - `results() -> GameResults`: a grade (S to D), per-player rows (kJ, average %FTP, time in band, custom stats), XP and cosmetic unlocks. The platform's results screen draws it, saves the ride and offers the Strava upload. `results()` runs on the host (or in solo play), and the platform sends the GameResults to every client. Then on every peer it calls `apply_progress(results: GameResults, progress) -> Array` (optional), which updates the local rider's `ctx.progress` and returns that rider's new unlocks, before the results screen shows them.
  - Signals: `lap_marker(label: String)` (becomes a FIT lap), `phase_changed(index: int)` (optional and informational, for a game whose riders share one phase sequence; the platform never relies on it) and `finished(reason: String)`. The GameHost tracks every rider's plan itself. Whenever a rider's phase changes (by duration, `max_s`, `end_phase` or `finished`), it emits `phase_started(peer_id: int, index: int)` on the EventBus, sends it in an `event` (5.5) and updates `frame.phase`.
- The GameHost (platform) owns the session around a game: lobby and ready-up, plan validation, the sim clock, routing directives to each rider's governor, warm-up and cool-down, pause (the game's sim clock stops; 4.1), rescue and AFK callbacks, telemetry, snapshots and events over the network, the ride recorder and its laps, and the results screen. Bots: when `bots` is true, the lobby offers pedal-scan Add bot and Remove bot entries up to `max_players`, and a bot FTP setting (default: the host's FTP, editable, sent in the `lobby_state` settings). A bot is named `Bot n`, has a negative peer id and `is_bot` true, and uses the bot FTP as a verified FTP. It runs Autopilot and rides MockTrainer's `erg` profile at compliance 1.0 (4.2). When a peer drops (`peer_left`), the GameHost calls `on_afk(peer, true)` at once and sets that rider's `frame.players[peer]` to `connected: false`, power and cadence 0 and an `age_s`; the slot stays until the session ends. A rejoin with the reconnect token gets `lobby_state`, its `plan`, its `phase` and the latest snapshot, and `on_afk(peer, false)` follows once fresh telemetry shows pedaling. A restarted client starts a new FIT file from the rejoin. After the token expires, the slot stays AFK. Once a session has started, the host refuses joins without a valid token with a `session_in_progress` message that the client shows.
- Determinism: rules are pure classes with `step(state, inputs, dt)`; they use only `ctx.rng` and never wall-clock time. The same seed and inputs give the same snapshots.
- Conformance: `tests/sdk/test_conformance.gd` runs every registered game through `configure`, plan validation, 2 minutes of headless `sim_step` with bots (or with Autopilot human slots when `bots` is false) at `min_players` and `max_players`, snapshot round trips through `JSON.stringify` and `JSON.parse_string`, a determinism check (two runs, same seed, same snapshot hashes) and `results`. A new game passes it without any change to platform tests. It also asserts that every `res://src/games/*/game.json` other than `_template` validates, naming the failing field, so an invalid game can't pass by being hidden.
- Tools for game sessions:
  - `tools/run_game_sim --game=<id> --content=<id> --players=<n> --bots=<n> --rider=<profile> --sim-speed=<x> --seed=<n> --report=<path>` runs a game headless with MockTrainer riders. `--players` counts human slots and `--bots` adds bot slots after them. `--rider` names a 4.2 profile: give it once for every human slot, or repeat it once per human slot in slot order. Optional flags: `--autopilot=all|none|<slot,…>` (default all), `--ftp=<w>[,<w>…]` (default 200 for every slot), `--unverified` (default: every FTP verified), `--haptics-off=<slot,…>`, `--options=<json>`, `--player-options=<json array, one object per slot>`, `--override=<json file>` (keys are file paths under `content/<id>/`, values are JSON merge patches applied before validation, for stress runs; recorded in the report) and `--max-sim-seconds=<n>` (default: the validated plan with every open-ended phase at `max_s`, plus 600). Every human slot has its own MockTrainer and governor. One human slot, with or without bots, runs as SOLO, so 4.6.4 pauses a coasting rider; two or more run as HOST with LoopbackTransport clients, so 4.6.4 marks AFK. A run ends when the cool-down finishes, at `--max-sim-seconds` (`end_reason: timeout`), or once a SOLO run has stayed paused for 120 s of platform time (`end_reason: paused`). However it ends, it calls `results()` and writes the report and FIT files. The JSON report holds: the arguments, `end_reason`, the events, each rider's phases (index, kind, start, end, `ended_by`), and every directive as requested and as applied (with `clamped_by`, or its refusal reason). It also holds a 1 Hz trace per rider {t, phase index, kind, mode, applied_target_w, applied %FTP, applied grade, clamped_by, rescue, afk, paused, haptic, power_w, cadence_rpm}, the sha256 and JSON byte size of every snapshot with `max_snapshot_bytes`, the results, and `fit_paths`: the ride recorder writes one FIT per human slot to `<report dir>/fit/<report stem>_slot<n>.fit`. Last comes `deterministic_hash`, a hash of the report without its paths, so two runs with the same arguments and seed match. `docs/GAME_SDK.md` lists every flag and profile.
  - `tools/new_game <id>` scaffolds every path from `src/games/_template/` and its content, assets and tests counterparts. It rewrites every `_template` path and the `Template` class-name prefix to the id (`siege` → `Siege`) in every copied file, renames files to match, and copies no `.uid` or `.import` files, so the new game never collides with `_template` or another game. It refuses, writing nothing and exiting 1, if any of its target paths already exists, so a resumed session can't overwrite a game.
  - `node tools/e2e/run.mjs --games=<ids>` plays each listed game's `e2e_content` with one host and two clients. It writes `build/e2e/<id>/report.json` (events per peer, applied directives, FIT paths) and, if `tests/games/<id>/e2e_check.mjs` exists, runs it with that path and fails on a non-zero exit.
  - `tools/screenshot --game=<id> --content=<id> --at=<seconds>[,<seconds>…] [--players=<n>] [--bots=<n>] [--rider=<profile>] [--autopilot=all|none] [--seed=<n>]` runs the game windowed (or under `xvfb-run`, section 2) with `run_game_sim`'s slot, role and profile rules. It steps the sim as fast as it can to just before each `--at` (in sim seconds), then renders at normal speed and saves a PNG of the full frame, HUD included, from the host's view.
  - `tools/art` (3.10).

- `src/games/_template/` is a tiny working game (one rider pushes a marker along a track in a 2D PixelViewport; a 5-minute warm-up, one 3-minute WORK phase at 75% FTP, a lap marker, results) that passes conformance and shows every SDK call in under 300 lines.

### 3.7 Reference game: Workout (P0, 1–8 riders, bots optional)

Workout is a group interval ride. It's useful on its own on training days, and it proves every platform path: ERG phases, SIM phases with virtual gears, ramped mode switches, warm-up, cool-down, rescue, laps, FIT, Strava, multiplayer and zero input.

- Sessions: built-in workouts in `content/workout/sessions/<content id>.json`, each opening with a 5-minute ramp from 50% to 65% FTP, except `e2e`, which stays inside the warm-up limits (4.6.8) throughout:

| Session | Main set | Recovery | Total |
| --- | --- | --- | --- |
| Easy 30 (`easy_30`; default, first-run and zero-input) | 20 min at 65% FTP, with three 30 s FREE sprints (SIM flat, virtual gears) at minutes 6, 12 and 18 | none | 28 min |
| Sweet spot (`sweet_spot`) | 2 × 12 min at 90% FTP | 4 min at 55% FTP between | 36 min |
| Threshold (`threshold`) | 3 × 8 min at 98% FTP | 4 min at 55% FTP between | 40 min |
| VO2 (`vo2`) | 5 × 3 min at 110% FTP | 3 min at 50% FTP between | 35 min |
| Rolling road (`rolling_road`) | 30 min of SIM on a procedural rolling course (grade −2% to +6%) | none | 38 min |
| E2E (`e2e`, the `e2e_content`) | a 60 s ramp from 50% to 60% FTP, 30 s ERG at 65% FTP, then a 30 s FREE sprint (SIM flat, virtual gears) | none | 2 min plus the 3-minute cool-down |

Every total except E2E's includes the 5-minute warm-up and the platform's 3-minute cool-down. VO2's 3-minute recoveries at 50% FTP satisfy the 4.6.1 reset (≤ 90% FTP for 120 consecutive seconds of ERG), so each 180 s block above 105% stays under the 300 s limit; Threshold's 8-minute blocks stay under the 105% cap for phases longer than 300 s. `e2e` keeps every target ≤ 65% FTP and its two mode switches 30 s apart, so the PlanValidator accepts it without a warning.
- `.zwo` import (Workout Director, P0): `addons/wattlands/sim/workout_import` parses SteadyState, Warmup, Ramp, Cooldown, IntervalsT and FreeRide (as SIM) with power as a fraction of FTP. Unsupported tags are skipped with a warning. The importer inserts a warm-up prefix if missing and clamps each block to 4.6 and the warm-up limits before the PlanValidator runs, listing each clamp and its reason in the session preview; the PlanValidator itself only accepts or rejects (3.6). Games reuse the same parser (for example to schedule Siege waves or fish bites from a workout).
- Ride view (2D, `pixel_base` [640, 360]): a simple side-scrolling landscape built from the world2d kit, with one colored pennant marker per rider moving at their speed (3.11), the course profile for SIM phases and the interval blocks drawn on the ground. No people are drawn.
- Free sprints and FREE phases use SIM with virtual gears (4.5); a sprint scores under `SprintRule`. Rolling road is one SIM phase (kind WORK) on its course, with a 76–105% FTP target band on the power gauge. Everything else is ERG.
- Multiplayer: everyone rides the same timeline at their own %FTP. The teammate strip shows each rider's compliance, and the group score is the average time in band.
- Results: time in band per interval and rider, kJ, average and normalized power, best 1-, 5- and 20-minute power, sprint peaks, a grade from time in band; FIT laps per interval. In band means power within ±5% of the applied target in ERG, power within 76–105% FTP in Rolling road, and cadence ≥ 60 rpm in FREE sprints. The grade comes from the session's time in band: S ≥ 95%, A ≥ 90%, B ≥ 80%, C ≥ 65%, otherwise D.
- Autopilot has nothing to choose in a session; with Autopilot or pedal UI on, the session picker and results run on pedal-scan.

### 3.8 Rides, FIT export and Strava (P0)

- Recorder (`addons/wattlands/rides`): every session records the local rider at 1 Hz (timestamp, power, cadence, speed, and distance from the trainer's reported speed), with a lap at each `lap_marker` from the game, at each plan phase marked `lap`, and at the start of the appended cool-down, which is always its own lap. On the results screen it writes `rides/<UTC start>_<game>.fit` and a JSON summary under `Paths.user_dir()`. Each rider keeps only their own ride; no ride or Strava data goes to the host or the relay.
- FIT encoder (pure GDScript): protocol 2.0 with a 14-byte header, header and file CRCs (the FIT SDK's CRC-16), and the messages file_id (type activity 4, manufacturer development 255), device_info, event (timer start and stop), record (with heart rate, field 3, when a sensor gives one), lap, session (sport cycling 2, sub_sport virtual_activity 58, totals, average and maximum power and cadence, average and maximum heart rate when known, total work) and activity. FIT timestamps count seconds from 1989-12-31 00:00:00 UTC (Unix time − 631065600). No GPS fields.
- Decoder check (`tools/fit_check`): decode every FIT file the tests write with Garmin's `@garmin/fitsdk` (npm, pinned; `Decoder.isFIT`, `checkIntegrity`, `read`), assert zero errors and the expected values, and take enum values from the SDK's profile. If npm is blocked, the qa agent writes an independent GDScript decoder for the same checks. Either way there is one command line, `node tools/fit_check/check.mjs <file|dir>... [--expect-laps=<n>] [--json]`. It decodes every FIT file given (directories recursively), prints per file its errors, record count, laps (start, duration) and session totals, and exits non-zero on any error. With npm blocked it runs the GDScript decoder through `tools/godot.sh`; that decoder lives outside the `.gdignore`d folder, for example `tools/fit_decode/decode.gd`.
- Connect: Settings → Strava takes the client ID and secret of the player's own Strava API app (README: create it at strava.com/settings/api with callback domain `localhost`). Connect serves a loopback callback with `TCPServer` on 127.0.0.1 for up to 5 minutes and opens the browser at `https://www.strava.com/oauth/authorize` with `response_type=code`, `approval_prompt=auto`, `scope=activity:write`, a random `state` and `redirect_uri=http://127.0.0.1:<port>/strava/callback`. Check `state`, then POST the client ID, secret and code to `https://www.strava.com/oauth/token` (`grant_type=authorization_code`). Strava's OAuth needs the client secret (it documents no PKCE), so the secret stays on the player's PC. Strava whitelists 127.0.0.1 like localhost, and the IP avoids browsers resolving localhost to IPv6. While the network lock is set, Connect fetches the authorize URL itself with `HTTPRequest` (following redirects; only loopback hosts are allowed then) instead of opening a browser, so the mock's redirect reaches the loopback callback. The tests and the end-to-end harness connect this way.
- Tokens: access tokens last 6 hours. Refresh with `grant_type=refresh_token` shortly before expiry and always keep the newest refresh token, because Strava rotates them. Send tokens only in the Authorization header (Strava requires headers from 2027). Keep the secret and tokens in `strava.json` under `Paths.user_dir()`, never in logs, telemetry, the relay, crash reports or git. Disconnect calls POST `https://www.strava.com/oauth/revoke` with HTTP Basic auth (client ID and secret) and the refresh token, then deletes them.
- Upload: a multipart POST to `/api/v3/uploads` (build the body for `HTTPRequest.request_raw()`) with `file`, `data_type=fit`, `trainer=1`, `name`, `description` and `external_id` (the ride's UUID), then poll GET `/api/v3/uploads/{id}` every 3 s for up to 2 minutes until it reports `activity_id` or `error`. Treat a duplicate as uploaded, refresh once on 401, back off on 429, and keep failed or offline uploads in `rides/upload_queue.json` for the next launch.
- Defaults: auto-upload is off. The results screen offers Upload to Strava (pedal-scan selectable), and a rider with auto-upload on gets it without a prompt. P1: Rides history with re-upload, and an opt-in import of FTP and weight from GET `/api/v3/athlete` (needs `profile:read_all`).
- Base URLs are settings (`strava_api_base`, `strava_oauth_base`; Strava has announced `https://api-v3.strava.com` from 4 January 2027), and `--strava-base=<url>` points both at the mock.
- Mock (`server/mock_strava`, tests only): zero-dependency Node on `node:http` serving authorize (redirects straight to the callback), token (both grants, rotating refresh tokens, a test clock for expiry), uploads (multipart parsing, a FIT header and CRC check, a processing-then-ready status, duplicates by `external_id`), upload status and revoke, with injectable 401, 429 and 500 responses.

### 3.10 Art pipeline (`tools/art`)

Game sessions make their 2D pixel art with `tools/art`, which calls fal.ai. This run builds it and tests it against a mock; it never calls the real fal.

- `assets/<id>/art.json`: `palette` (at most 32 hex colors), `style` (a prompt prefix shared by every sprite), `endpoint` (default `openai/gpt-image-2.5/sunburst/text-to-image`; `openai/gpt-image-2.5/flare/text-to-image` for cheap drafts), optional `quality` (default `high`, sent where the endpoint takes it) and `sprites`, each {`id`, `prompt`, `size` (art pixels, for example `[96, 48]`), `background` (`transparent` by default, `opaque` for backdrops), `parts` (optional named sub-sprites cut by rectangles), `anchor`, optional `align` (where a fitted sprite sits, default `bottom_center`), and optional `tile` and `mirror`}.
- `node tools/art/generate.mjs --game=<id> [--only=<ids>] [--dry-run] [--budget=<usd>] [--reroll=<ids>] [--select=<sprite id>:<request id>] [--mock=<url>]`, zero-dependency Node:
  - one request per sprite at the model's nearest valid size with the sprite's aspect, within the endpoint's limits kept in `tools/art/endpoints.json` (both sides multiples of 16, at least 655,360 pixels, and the endpoint's maximum edge and aspect; assume 3840 pixels and 3:1 where fal doesn't state them); a sprite outside those limits is requested at the nearest allowed aspect and listed by `--dry-run`; `background` as set, `output_format: png`;
  - raw results cached in `.art_cache/<id>/` (gitignored);
  - every request (endpoint, full input, request id, estimated cost) recorded in `assets/<id>/art_manifest.json`;
  - before paying for a sprite, it looks for a paid result with the same input from the last 24 hours (`GET https://api.fal.ai/v1/models/requests/by-endpoint?expand=payloads`) and downloads that instead;
  - it stops before the run's estimated spend passes `--budget` (default $10), and `--dry-run` prints the plan and cost;
  - Prices: `tools/art/prices.json` holds a conservative estimate per endpoint and quality: sunburst at high quality is $0.07 an image up to 1536 × 864, scaled by pixel count above that; flare uses its listed price, else the sunburst figure. Every request sets `quality` explicitly where the endpoint takes it (`high` unless art.json says otherwise). When fal reports a billed amount, the manifest records it beside the estimate, and the budget stop sums the larger of the two. `--reroll=<ids>` skips the cache and the 24-hour reuse and pays for new results. The manifest marks one `selected` result per sprite (the newest by default; `--select=<sprite id>:<request id>`), and pixelate uses only that one.
  - real calls need both `FAL_KEY` and `WATTLANDS_ALLOW_ART=1`; without them it refuses unless `--mock` is given. The art lock replaces the network lock for this one tool: `generate.mjs` doesn't read `WATTLANDS_NO_NETWORK_INTEGRATIONS` (which governs the app's Strava client), so a game session can keep the network lock on for everything else. It contacts only fal's hosts and never prints the key.
- `tools/godot.sh --headless --path . -s tools/art/pixelate.gd -- --game=<id>`: trims transparent margins and never stretches. A transparent sprite is fitted inside `size` with its aspect kept and padded with transparency toward `align`. An opaque sprite is scaled to cover `size` and centre-cropped. A `tile: true` sprite (one segment within the endpoint's aspect) is scaled to the sprite's height and repeated across its width, alternating flipped copies with `mirror: true`. It then downsamples with area averaging, quantizes to `palette` (nearest color in Oklab, no dithering by default), cuts `parts` and writes `assets/<id>/sprites/<sprite id>.png` (committed) with the pixel import preset. Re-runs are deterministic.
- `tools/art/mock_fal` (Node, tests only) serves queue submit, status, results with generated PNGs and the by-endpoint listing, so tests cover generation, recovery, the budget stop and pixelation end to end.
- Animate by parts, not frames: gears and flywheels rotate, pistons slide, chains scroll, fish and water wobble by shader. Draw extra frames only where parts can't do the job.
- Credit the art as generated with OpenAI's GPT Image 2.5 through fal in `docs/credits.d/<id>.md`. Prompts never name brands, logos, real insignia or existing characters.
- `docs/ART_PIPELINE.md` explains setup (`FAL_KEY`, `WATTLANDS_ALLOW_ART=1`, budgets, adding fal credits), writing `art.json` for consistent sprites (one shared style prefix, a fixed palette, transparent backgrounds, sizes in art pixels), the part-animation approach, and recovering a paid result after a failed download.

### 3.11 Speed model (`addons/wattlands/sim`)

Games that move a vehicle (the Workout ride view, Tank Crew's driver, a future Kart Rush) share one speed model. Integrate speed every sim step from P_eff: `v += dt·(η·P_eff / max(v, 1) − m·g·(Crr·cosθ + sinθ) − 0.5·ρ·CdA·(v + v_wind)·|v + v_wind|) / m`, with v ≥ 0, Crr 0.004, CdA 0.32 m², ρ 1.225, η 0.97 and m = the scaling mode's rider mass plus 8 kg; a game may pass its own CdA, mass offset and a visual speed multiplier for game feel. Tests use the steady-state equation `P·η = v·(m·g·(Crr·cosθ + sinθ) + 0.5·ρ·CdA·(v + v_wind)²)`, solved by bisection on [0, 30] m/s, as the oracle.

## 4. Trainer integration

### 4.1 Layers

```
BleTransport (interface)        GdbleTransport | BridgeTransport | (P2) DirconTransport
  FtmsClient                    discovery, subscriptions, control-point queue, parsing
    TrainerDevice (interface)   FtmsTrainer | MockTrainer
      TrainerController         modes ERG / SIM / RESISTANCE / OFF, slew, coalescing
        SafetyGovernor          the only path that can change resistance
          GameHost              plans and DirectiveSink; games request EffortDirectives (3.6)
```

Telemetry flows up as `TrainerSample {t, power_w, cadence_rpm?, speed_kmh?, flags}`.

Pause never uses `SceneTree.paused` for system nodes. The GDBLE manager, FtmsClient, TrainerController, SafetyGovernor, MockTrainer, NetSession and its transport, the GameHost, the input router and the GestureRecognizer run with `process_mode = PROCESS_MODE_ALWAYS`. Pausing stops the game's sim clock and puts the trainer at the ERG floor or SIM flat, while telemetry, indications, reconnect and panic keep working. A test pauses the tree and asserts that mock samples and a control-point response still arrive.

### 4.2 Backends

- GdbleTransport (P0): vendor GDBLE (github.com/Fantety/GDBLE; MIT; Rust GDExtension on btleplug 0.12; Windows 10+ x86_64) into `addons/gdble`, pinned by commit with SHA-256 sums. ### 4.4 Connection flow

Scan (advertised 0x1826, or a name containing KICKR), connect, discover, read features and ranges, subscribe to 0x2AD2 and 0x2ADA, enable indications on 0x2AD9, Request Control, set SIM flat (grade 0), ready. Serialize control-point writes: one in flight, 2 s timeout, two retries. If Request Control fails with 0x05, or status reports 0xFF, tell the player another app (Zwift, the Wahoo app) may hold control. On disconnect, reconnect with exponential backoff (1, 2, 4, 8 s, max 15 s), resubscribe, re-request control and restore the last safe mode. Remember the last device. A heart rate sensor (service 0x180D, measurement 0x2A37; chest straps and watches broadcasting heart rate) pairs in Settings (Trainer > Sensors) alongside the trainer: subscribe only, never written to, remembered and reconnected the same way.

### 4.5 Control strategy

- ERG for sustained phases; SIM for racing, sprints and haptics; RESISTANCE only as a P1 fallback.
- KICKR facts to respect: 1800 W max; grade −10% to +16%; ERG takes seconds to settle and can overshoot at high power; bike data arrives about once per second; trainer cadence is an estimate that lags after sprints. Firmware before 1.5.5 could spike to 2000 W when switching between ERG and SIM, so the README recommends current firmware, and every mode switch is ramped. Before ERG → SIM, the controller sets the ERG target to min(applied target, the rider's 3 s power), then enters SIM at grade 0 before applying the stacked grade. Before SIM → ERG, it sets SIM grade 0, then enters ERG at min(the rider's 3 s power, the planned or directed target), never below the floor, and slews up under 4.6.2. A SIM → ERG entry never sets a target above the planned or directed target. The PlanValidator warns when two switches between ERG and SIM are less than 30 s apart. At run time the same 30 s spacing holds for switches made by directives, except the two switches that bracket one directive SIM block of 10–30 s (3.6). The DirectiveSink refuses a block shorter than 10 s, or one that starts less than 30 s after the rider's previous switch.
- SIM parameters follow the stacking rule in 4.6.6. Defaults: crr 0.004 and cw 0.51 kg/m, both configurable. Games only scale cw relatively (drafting, wind haptics); game physics uses its own CdA.
- Coalescing: at most 2 control writes per second; drop superseded commands; always send the newest.
- Virtual gears (P0, for single-speed Zwift Cog riders and useful with a cassette): 24 gears on shift_up and shift_down. Implement each gear as a grade offset in SIM, tuned so one step changes resistance at constant flywheel speed by about 6–8%; show the gear on the HUD and document the approximation. Zwift Click shifting itself works only inside Zwift.
- Cadence: use FTMS cadence when present; estimate it from speed when absent or stale (learn the speed-to-cadence ratio while both are valid, or run a 10 s calibration at 90 rpm). Gestures in ERG use relative speed change, which needs no calibration.

### 4.6 Safety governor (P0, every rule unit-tested)

1. ERG clamps: floor max(30% FTP, 50 W); absolute ceiling min(150% FTP, 1000 W, the trainer's Supported Power Range max). Applied ERG targets are whole watts. The governed target is rounded down (the floor is rounded up), and the caps and duration counters compare that whole-watt value, so a target exactly at a cap is neither reported as clamped nor counted above it. Duration limits count time with the applied target above 105% FTP (300 s) and above 120% FTP (60 s). When a limit is reached, the ceiling drops to that band and stays there until the applied target has been ≤ 90% FTP for 120 consecutive seconds of ERG (inclusive), which resets both counters. A switch to SIM restarts that count, and time in SIM adds nothing to either limit. Phases longer than 300 s cap at 105% FTP, where a phase's length is its planned `duration_s` or, for an open-ended phase, its `max_s` (3.6), and the cap covers every directive inside it. While FTP is unverified, every ERG target is multiplied by 0.85. The FTP test's ramp_test profile (3.2, P1) is the only exception to the duration limits, the 105% cap for phases longer than 300 s, the 150% cap and the unverified factor; rescue (which ends the test), coasting, slew, the floor, panic and the min(1000 W, Supported Power Range max) ceiling still apply. Sprints happen in SIM.
2. Slew: increases at most 30 W/s; decreases immediately.
3. Rescue: in ERG with a governed target ≥ 60% FTP (the plan or directive target after the unverified-FTP factor and the 4.6.1 caps, before slew), if cadence < 45 rpm for 3 s or power < 75% of the applied target for 5 s, drop to 50% FTP, show "rescue", hold until cadence ≥ 70 for 3 s, then ramp back over 10 s. Rescue state goes out in telemetry. Games treat rescue as a stagger (`on_rescue`, 3.6), never a wipe.
4. Coasting: `not_pedaling` (3.5) for 3 s, timed from the first sample that meets it, drops ERG to its floor; after 10 s, pause (solo) or mark AFK (multiplayer). A solo rider is normally already paused at 5 s by the pause on not pedaling (3.5).
5. Panic: `SafetyGovernor.emergency_safe()` turns ERG off and sets SIM grade 0 and wind 0 immediately; the trainer stays safe until the player resumes.
6. SIM stacking: base grade = (course grade + mode grade) × difficulty (default 50%) + virtual-gear offset, clamped to the user's range (default −5% to +10%). Mode grade (a game's own load, such as Tank Crew's boiler) is not a haptic. Haptic grade (hits on a tank, a fish's last runs) × the intensity setting adds at most +3% for at most 8 s, with a 15 s cooldown per receiver, counted from the end of that receiver's previous applied haptic; haptic wind is limited so its added force at the current speed is no more than that of +3% grade. Haptics are off during warm-up and for riders who opted out. The total is clamped to −10% … +16%. A directive's `crr` and `cw` are relative factors in [0.5, 1.0], so they can only lower resistance; added wind comes only as a haptic, bounded as above. A haptic for a rider in ERG is dropped and logged, never turned into a mode switch. `target_w` and `target_wkg` are converted to %FTP before every 4.6 check.
7. The network never sends device commands. Hosts send EffortDirectives; each client validates and clamps them locally and reports what it applied.
8. Warm-up: the first 5 minutes of riding, counted from the first pedal stroke after the trainer connects, and reset after 20 minutes without pedaling. During it, ERG targets stay ≤ 65% FTP, SIM grade stays within −2% … +3%, and haptics are off. Autopilot never skips it; a player may skip it in settings. Every game opens with warm-up content (Workout's ramp-in, each game's own diegetic warm-up, the FTP test's ramp-in), and the PlanValidator enforces it (3.6).
9. On exit, crash paths and disconnect: try SIM flat, then Stop (0x08 0x01).
10. Tests use MockTrainer only, and the hardware lock (section 1) blocks control writes in every process this run starts.
11. Structure: only SafetyGovernor holds TrainerController; only TrainerController calls TrainerDevice setters; only FtmsTrainer calls `FtmsClient.write_control()`. `tests/arch/test_no_bypass.gd` scans `res://addons/wattlands` and `res://src` and fails on any other call site of `write_characteristic`, `write_control`, `set_target_power`, `set_simulation` or `set_resistance`. Games under `src/games/` are covered automatically.
12. Precedence: panic (rule 5) overrides everything. Otherwise the applied ERG target is the plan or directive target × the unverified-FTP factor, limited by the rule 1 ceilings and duration limits and by the warm-up cap (rule 8). During rescue it is 50% FTP instead, and while coasting (rule 4) it is the floor, which wins over rescue. The floor max(30% FTP, 50 W) wins over every cap and over rescue's 50% at low FTP (50 W is above 65% FTP below an FTP of 77 W, and above 50% FTP below 100 W). Slew (rule 2) applies last, to increases only.

## 5. Multiplayer

### 5.1 Model

Star topology through a relay. The host's game is authoritative and simulates at 20 Hz. Clients send telemetry and intents; the host sends snapshots, events and effort directives. Fitness pacing tolerates 100–200 ms of latency, so clients predict their own rider locally and reconcile softly toward the host.

### 5.2 Room codes

Six characters from the Crockford Base32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, displayed as `K7Q-X2M`. Input is case-insensitive and maps O to 0 and I or L to 1. The relay generates codes; in P1 a host may request their previous code if it is free.

### 5.3 Relay server (`server/relay`, P0)

Node.js 22.12+ (whatever is on PATH), TypeScript, no database. Prefer the `ws` package; if `npm install` fails, implement the server with zero dependencies on `node:http` upgrade plus `node:crypto` (RFC 6455 handshake; text, close, ping and pong frames; client masking; 16 KB maximum payload; no extensions). Run TypeScript with Node's built-in type stripping using only erasable syntax (no enums, namespaces or parameter properties; add `--experimental-strip-types` on Node 22.12–22.17). Test with `node:test` and Node's global WebSocket client. `GET /health`, WebSocket at `/v1`, default local URL `ws://localhost:8787/v1`. One relay serves every game; it never looks inside `d`.

```
-> {"t":"hello","proto":1,"game":"wattlands","build":"0.1.0"}
-> {"t":"create","max":8}
<- {"t":"created","code":"K7QX2M","peer":1,"token":"..."}
-> {"t":"join","code":"K7QX2M","token":null}
<- {"t":"joined","peer":3,"host":1,"token":"..."}
<- {"t":"error","code":"room_not_found|room_full|version_mismatch|rate_limited|bad_request"}
-> {"t":"msg","to":1,"d":{...}}        to: a peer id, the host id, or 0 for everyone
<- {"t":"msg","from":3,"d":{...}}      non-hosts may only send to the host
<- {"t":"peer_joined","peer":3}
<- {"t":"peer_left","peer":3,"reason":"..."}
<- {"t":"host_left"}
-> {"t":"ping","ts":123}   <- {"t":"pong","ts":123}
```

Limits: 8 peers per room, 16 KB per message, 60 messages/s per peer (burst 120), 60 s idle timeout (clients ping every 15 s), 10 join attempts per minute per IP, 4 h room lifetime. `to: 0` means everyone except the sender. A reconnect token stays valid for 120 s and keeps the same peer id; clients save it in their profile dir. When the host's socket drops, the relay sends `peer_left` for peer 1 with reason "dropped" and holds the room for 120 s; `host_left` goes out only on an explicit leave or when the host's token expires. Ship a Dockerfile, a README and tests for create, join, leave, broadcast, limits, reconnect, host drop, host_left and malformed input; example `fly.toml` and `render.yaml` are P1.

### 5.4 Godot networking (`addons/wattlands/net`)

`Transport` interface: signals `connected`, `disconnected(reason)`, `peer_joined(id)`, `peer_left(id)`, `message(from, data)`; methods `host()`, `join(code)`, `send(to, data)`, `poll()`. Implementations: RelayTransport (WebSocketPeer; ws or wss URL from settings or `--relay`), LoopbackTransport (tests, P0), LanTransport (P1: the host serves the same relay protocol on a local WebSocket server, plus UDP broadcast discovery). A `NetSession` autoload owns lobby state, roles, routing, clock offset (from ping), snapshot buffers and reconnect.

### 5.5 Game messages (inside `d`)

- `player_info` (client to host): name, color, FTP, `ftp_verified`, `p_eff_per_w`, weight only if opted in, preferred cadence, haptics on or off, Autopilot flag, `player_options` values, installed games with their versions.
- `lobby_state` (host to all): players, trainer status, ready flags, `game_id`, `game_version`, `content_id`, scaling, settings (including the game's `options`), and each player's `player_options` values. A client that lacks the game or has another version can't ready up and sees a clear message.
- `telemetry` (client to host, 5 Hz): t, power, cadence, speed, effort, p_eff_w, W′bal, applied_target_w, clamped_by, rescue, afk, seconds left above 105% and 120% FTP, gestures, intents.
- `snapshot` (host to all, 10 Hz): `{game_id, seq, state}` where `state` is the game's `snapshot()`.
- `event` (host to all): phase changes, results and the game's own events (`apply_event`).
- `plan` (host to each client, after validation at the start and after every `replan`): that rider's validated EffortPlan, which the client re-validates before its governor uses it.
- `phase` (host to each client): the rider's phase index, the host sim tick at its start and `ended_by` (duration, max_s, end_phase or finished), sent on every change and on rejoin.
- `directive` (host to one client): {`kind`, …}, where `kind` is `request` (an EffortDirective {mode, target_pct or target_wkg or target_w, mode_grade, haptic, crr, cw, duration_s, reason, source}), `course_grade` (grade_pct), `cadence_band` (lo_rpm, hi_rpm) or `power_band` (lo_w, hi_w).
- `roster` (host to all, 2 Hz): per slot, raw W, cadence, %FTP, rescue, afk, connected and the latest `teammate_status`. The teammate strip draws it on every peer, and games read it as `ctx.roster`, for example to show other lanes' W and rpm.

`Protocol.decode()` converts peer, host, from, to, seq, proto, max and every `*_id` field to int (Godot's JSON parser returns every number as a float) and rejects any message that fails its schema; games declare the int fields of their own snapshot and event payloads (`int_fields()`, 3.6) so the same conversion applies. Dictionaries are keyed by int peer id, and protocol tests round-trip through `JSON.stringify` and `JSON.parse_string`. Version every schema and show a clear error on mismatch. Players ready up with `pedal_start` or confirm. If the host leaves, end the session gracefully (host migration is P2).

## 7. Testing and verification gates

Test-harness rules (also in `CLAUDE.md`): never pass `-d` or `--debug` to an automated Godot run (a script error then hangs at the debugger prompt or exits 0); close stdin and wrap every run in a timeout. No Godot process starts another Godot process: a check that needs its own import or Godot run is a separate `tools/run_tests` step, started after the previous Godot process has exited. Unit tests use GUT 9.7.1, the release for Godot 4.7.x: `tools/godot.sh --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -ginclude_subdirs -gexit -gjunit_xml_file=build/junit.xml`. `tools/run_tests` passes only if the exit code is 0, "Run Summary" appears in the log, the JUnit test count is above 0 and at least the previous green count, and the log contains none of "SCRIPT ERROR", "Parse Error", "Debugger Break", "Ignoring script" or "Nothing was run". GUT fails a test on any unhandled `push_error`, so tests of code that rejects bad input use `assert_push_error()`, and expected non-fatal conditions (such as no Bluetooth adapter) use `push_warning`. The test directory includes `tests/games/` so every game's tests run in the one suite.

## 9. Definition of Done and final report

- Every P0 item is implemented, reachable from the menus and covered by tests. Every gate in section 7 is green (hardware excepted), or listed as known failing in the final report with no threshold or assertion weakened.
